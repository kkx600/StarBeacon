# 星烽 StarBeacon 发布与验收流水线

工程检查、发行包核验和正式版本前的业务验收分别记录。任一阶段失败、跳过或缺少输入，都不能以其他阶段的成功代替。

## 工程检查

`.github/workflows/ci.yml` 在推送 `main`、`codex/**` 及拉取请求时运行，也由版本发布工作流通过 `workflow_call` 复用。Go 部分包括依赖校验、质量与工具脚本测试、功能／接口／页面契约对齐、构建、race 测试、`go vet`、集成测试编译（`-tags=integration,captureintegration`，不连接依赖服务）、格式检查和 Linux amd64／arm64 交叉编译。前端通过 `scripts/qualify_frontend.py` 执行工具测试、组件覆盖率（四项均不低于 90%）、严格类型检查与双端构建，并上传 `starbeacon-frontend-evidence`；即使执行失败，也保留已有原始日志与逐文件源码清单。原型执行覆盖、工作区、采集器与配色检查及构建。

原型截图是设计参考。默认检查只核对图库完整性（文件、JPEG 尺寸、横向溢出、浏览器来源与 SHA-256）；界面源码变化后截图会过期，CI 以警告注解提示过期数量，不阻断合并或发布。需要证明截图与当前界面一致时运行 `node prototype/scripts/check-screenshots.mjs --strict`，重新捕获后用 `--refresh` 更新来源清单。

源码清单与摘要算法见[前端工程](../web/README.md)。工程证据不包含全部业务验收声明。

Go 集成回归先通过官方 `go test -list` 固定顶层用例清单，超过 64 项时分为两组顺序执行。同一依赖环境不并行修改业务夹具；每组保留 race、单次执行、1200 秒 Go 包级期限和 1260 秒外层期限，业务请求与子进程期限不变。执行清单必须无遗漏、无重复、无失败或跳过，合并时重新核对每组原始日志及覆盖文件。远程控制器的 3000 秒观察预算用于容纳两组、单元与整理阶段，不属于业务响应时间指标。

## 标签发布

推送 `v主版本.次版本.修订版本` 标签即触发 `.github/workflows/release.yml`，同一运行内依次执行：

1. **核对版本标签**：`scripts/check_release.py identity` 校验标签格式，通过 GitHub API 解析标签（含附注标签）实际指向的提交，要求与触发提交一致且已合入 `main`。
2. **工程检查**：复用 `ci.yml` 的全部检查，任何一项失败都不打包。
3. **构建 Linux 发行包**：检出冻结提交并构建前端，在离线、只读、非 root、去除全部能力且限制内存与 CPU 的容器中执行 `scripts/package_linux.py`，产出平台与采集器各一个 Linux amd64 ZIP 及 `checksums.json`。打包时核验 UPX 压缩与解压还原、压缩后程序的实际版本回读、项目与前端许可、Go 依赖许可和逐程序 CycloneDX SBOM。
4. **结构核验与发行说明**：`check_release.py verify` 复核清单、两个 ZIP 的名称集合、摘要、包内路径与权限、ELF 架构、许可与依赖目录；`notes` 以 `docs/releases/<版本>.md`（存在时）为正文，附加来源提交、本次运行链接与 SHA-256 表。
5. **发布**：下载制品后再次核验，确认标签仍指向同一提交，删除失败运行遗留的同版本草稿，再创建 GitHub Release 并上传两个 ZIP 与 `checksums.json`。带后缀的标签（如 `v0.2.0-rc.1`）发布为 Prerelease，不占用 Latest；已发布的版本不覆盖，需要修正时使用新的版本号。

```sh
git switch main
git pull --ff-only
git tag -a v0.2.0-rc.1 -m "StarBeacon v0.2.0-rc.1"
git push origin v0.2.0-rc.1
```

任一步骤失败时，在 Actions 运行页面使用 Re-run failed jobs 重试；不要移动已推送的标签，标签被移动后发布会停止。打包容器的依赖诊断在失败时上传为 `starbeacon-release-diagnostics`。

标签发布只证明同一提交通过工程检查、发行包结构完整，不代表 107 项产品需求、生产部署或客户环境验收。

## 正式版本前的验收

107 项需求全部通过不再作为自动发布门禁：它把尚未开始的远期能力与首发核心闭环绑在一起，任何一项缺失都会阻断全部发行。是否发布不带后缀的正式版本，由[核心功能与发布验收](核心功能与发布验收.md)列出的核心闭环、同源远程端到端结果与生产部署检查（TLS、最小数据库权限、原生隔离、独立网络、干净提交）共同决定。逐项需求状态继续在[功能实现与验收状态](功能实现与验收状态.md)中跟踪，执行结果记录在[测试覆盖与验收记录](测试覆盖与验收记录.md)。

已有的原生引擎、实际网卡、数据库、消息队列、检索、通知协议与工程页面子流程证据只适用于对应的冻结来源，不能自动扩展为未实现业务的通过记录。

远程工程项目默认使用 `/var/lib/starbeacon-acceptance/<项目标识>` 保存专有配置、设备身份和挂载依据，数据库等状态继续使用该项目的独立 Docker 卷。项目父目录由部署账号独占，拒绝链接、共享写权限和同名接管；源码、报告及一次性缓存分别管理。历史 `/tmp/starbeacon-acceptance-*` 状态仅用于原项目核对，不在原目录丢失时创建空身份并冒充恢复。主机临时目录和临时 Docker 容器不能作为持久身份及恢复依据。

`scripts/remote_review.py` 支持通过 `--state` 与 `--review` 显式绑定独立项目和工程实例状态，仍核对项目、目录、数据库及源码归属；新实例不覆盖历史状态文件。

## 失败与保留

验收报告、原始覆盖率、失败日志与源码快照分别归档。超时记录实际期限和未知子进程退出码，不推定成功或伪造退出码。修复后的执行使用独立目录，历史失败不覆盖；报告必须明确开发环境、临时存储与生产存储的差异。

独立工程实例可通过 `remote_review.py --state <项目状态> --review <实例状态> --capture <该实例采集状态>` 选择对应的采集器登记。没有登记时使用该实例专用的不存在路径，避免误读其他项目的全局采集状态；文件存在时仍核对项目、实例目录、内部网络和最小能力，不能借参数接管其他实例。
