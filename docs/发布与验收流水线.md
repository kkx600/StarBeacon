# 星烽 StarBeacon 发布与验收流水线

工程检查、完整业务验收和发行包验证分别记录。任何阶段失败、跳过或缺少输入，都不能以其他阶段的成功代替。

## 工程检查

`.github/workflows/ci.yml` 检查 Go、工程契约、前端与原型。前端通过 `scripts/qualify_frontend.py` 执行工具测试、组件覆盖率、严格类型检查与双端构建，并上传 `starbeacon-frontend-evidence`。即使执行失败，也保留已有原始日志与逐文件源码清单。

源码清单与摘要算法见[前端工程](../web/README.md)。工程证据不包含全部业务验收声明，不能直接用于正式发布。

Go 集成回归先通过官方 `go test -list` 固定顶层用例清单，超过 64 项时分为两组顺序执行。同一依赖环境不并行修改业务夹具；每组保留 race、单次执行、1200 秒 Go 包级期限和 1260 秒外层期限，业务请求与子进程期限不变。执行清单必须无遗漏、无重复、无失败或跳过，合并时重新核对每组原始日志及覆盖文件。远程控制器的 3000 秒观察预算用于容纳两组、单元与整理阶段，不属于业务响应时间指标。

## 完整验收输入

远程执行器应在独立 Docker 环境生成 `acceptance.json` 与全部原始证据，并以 `starbeacon-acceptance-input` 上传至本仓库 main 同一提交的成功工程运行。输入必须包含全部 107 项真实断言、Go 和前端覆盖率、生产部署、双端七档 PC 全路由交互以及实际发行包证据。

当前完整远程业务断言执行器尚未交付。已有的原生引擎、实际网卡、数据库、消息队列、检索、通知协议与工程页面子流程证据，不能自动扩展为未实现业务的通过记录。

## 正式验收入口

`.github/workflows/acceptance.yml` 为手动触发的证据核验入口，输入 `evidence_run_id`。入口只接受本仓库 main、相同提交、成功完成且由 push 或人工触发的工程运行；拒绝 PR、其他仓库、其他提交、预览发行运行、重复或过期制品。它读取报告作为数据，不执行制品内脚本。

`scripts/check_acceptance.py` 继续核对全部 107 项需求、真实执行类型、逐项证据摘要、完整覆盖率、生产 TLS、最小权限、原生隔离、独立网络、干净提交和双端七档全路由交互。缺少完整输入时入口失败，不生成合格制品。

全部检查通过后，入口才上传 `starbeacon-acceptance`，供发行工作流引用。本入口校验已有的实际执行证据，不代替远程执行器，也不补造缺失业务断言。

## Linux 发行

`.github/workflows/release.yml` 要求同一提交成功的正式验收运行，再构建平台和采集器两个 Linux amd64 ZIP，核对实际 UPX 程序、制品摘要及发行包端到端验收身份。工程预览继续使用独立工作流，不授予正式版资格。

## 失败与保留

验收报告、原始覆盖率、失败日志与源码快照分别归档。超时记录实际期限和未知子进程退出码，不推定成功或伪造退出码。修复后的执行使用独立目录，历史失败不覆盖；报告必须明确开发环境、临时存储与生产存储的差异。
