# 星烽 StarBeacon 联动插件设计

本文定义联动插件的功能和交付契约。模板运行器和草稿版本目录见第 3 节，脚本及发布流程见后续章节。现有固定接口的配置与任务契约见[HTTP 联动与限时封禁](HTTP联动与限时封禁.md)。各项工程进度和验收依据见[功能实现与验收状态](功能实现与验收状态.md)。

决策日期：2026-11-20。防火墙、EDR、WAF 都在客户内网，每家的接口都不一样。平台不去逐家内置适配，而是让采集器运行**用户自己写的插件**：采集器在内网访问设备，拉取设备告警，执行封禁、解封、隔离。

## 1. 两种写法

| 写法 | 内容 | 适用 | 能做什么 |
| --- | --- | --- | --- |
| **模板** | 一份声明式配置：请求地址、参数、认证方式、成功条件 | 接口规整的设备，占大多数 | 固定的请求与字段映射，不能写逻辑 |
| **脚本** | 一段类 Python 的脚本（Starlark），调用平台提供的函数 | 要多步登录、签名、翻页或特殊判断的设备 | 条件、循环、函数、数据转换；不能访问文件、进程和任意网络 |

先用模板，模板表达不了再用脚本。两种写法共用同一套入口、试运行、签名和下发流程，在平台上是同一种对象。

也可以把设备接口文档里登录、黑名单、告警查询这几段贴进来，让 AI 生成草稿（第 7 节）。

## 2. 插件要实现的入口

一个插件按设备能力实现其中几项，没实现的能力在页面上不可选。

| 入口 | 作用 | 输入 | 返回 |
| --- | --- | --- | --- |
| `health` | 检查设备可达、凭据有效 | — | 是否正常及原因 |
| `pull_alerts` | 拉取设备上的新告警 | 上次拉到的位置 | 归一化后的告警列表 |
| `block` | 封禁地址 | 目标地址、时长 | 设备是否接受；可附带设备规则标识等信息 |
| `unblock` | 解除封禁 | 目标地址、封禁时保存的信息 | 设备是否接受 |
| `verify` | 回读设备，确认规则在不在 | 目标地址、封禁时保存的信息 | 存在、不存在或无法确认 |
| `isolate`、`release` | 隔离主机、解除隔离（EDR） | 主机标识 | 设备是否接受 |

`block` 和 `isolate` 必须同时实现对应的解除入口和 `verify`，否则不能签名：平台的限时封禁、到期解除和结果核对都依赖它们。`block` 返回的附加信息（例如设备给出的规则标识）随这次封禁的租约保存，解除和回读时通过 `lease` 取回。

拉取到的设备告警统一成这些字段后进入平台，与网络告警走同一条研判和关联流程，来源标记为“设备告警 · 插件名”：

| 字段 | 说明 |
| --- | --- |
| `id` | 设备侧的告警标识，用于去重 |
| `time` | 发生时间 |
| `severity` | 严重、高危、中危、低危 |
| `name` | 告警名称 |
| `source_ip`、`destination_ip` | 源和目的地址，可缺省 |
| `host` | 终端名称或标识（EDR） |
| `raw` | 设备原始记录，原样保留 |

## 3. 模板写法

```yaml
id: fw-vendor-b
device: 防火墙 · 厂商 B v5
allow_hosts: [192.0.2.20]           # 只允许访问这些地址
auth:
  login: {method: POST, path: /api/login, body: {user: "{{secret.username}}", pass: "{{secret.password}}"}}
  token: "{{response.json.token}}"   # 过期后自动重新登录
  header: "Authorization: Bearer {{token}}"
actions:
  block:
    request: {method: POST, path: /api/blacklist, body: {ip: "{{target.ip}}", ttl: "{{duration_seconds}}", comment: "{{task_id}}"}}
    success: "{{response.status == 200 and response.json.code == 0}}"
    save: {rule_id: "{{response.json.id}}"}   # 随租约保存，解除和回读时用
  unblock:
    request: {method: DELETE, path: "/api/blacklist/{{lease.rule_id}}"}
    success: "{{response.status in [200, 404]}}"
  verify:
    request: {method: GET, path: "/api/blacklist/{{lease.rule_id}}"}
    present: "{{response.status == 200}}"
```

模板里只有取值和布尔判断，没有循环和自定义函数。

### 模板契约与草稿版本

工程接口使用 `response.template.v1` 的 JSON 声明。每个步骤的 `accept.status` 列出可接受的状态码，`field` 和 `equals` 可选填一个平面 JSON 字段及对应的字符串、整数或布尔值。绑定、输出字段和相对路径用法见[验收设备模板](../internal/response/testdata/owned_acl_template.json)。

- 设备运行绑定包括固定管理 IP、受信 CA、目标及保护网段和租约上限。登录配置指定用户、密码和令牌字段名。采集器从私有文件读取凭据，令牌在内存中按 `ttl_seconds` 缓存。设备返回 401 时重新认证一次只读请求。写请求按任务标识进行独立核对。
- 封禁提交任务标识、目标、所有者和绝对到期。回读按任务标识匹配设备、所有者、目标、期限和规则标识。采集器把确认过的规则标识保存到本地租约，解除时同时使用规则标识和所有者条件。明确不存在仅用于创建前核对，解除结果需要设备回读确认。
- 管理员通过 `GET /api/v1/response-plugins` 读取当前草稿，使用 `after` 续页。`POST` 需要 `expected_version` 和 `Idempotency-Key`，初版的 `expected_version` 为 0。`GET /api/v1/response-plugins/{id}/versions/{version}` 读取具体历史版本。当前为 `draft`，被新版本替代后显示 `superseded`，版本内容及摘要保持固定。每租户最多 64 个模板，每个最多 32 个版本。
- 模板运行器的封禁、回读和解除由隔离 HTTPS 设备夹具验收。平台启用模板需要第 6 节的试运行、签名和设备下发流程。

## 4. 脚本写法

```python
def _headers(ctx):
    if state.get("token") == None:
        resp = http.post(ctx.base_url + "/login", json = {"user": secret.get("username"), "pwd": secret.get("password")})
        if resp.status != 200:
            fail("登录失败：%d" % resp.status)
        state.set("token", resp.json()["token"], ttl = 1500)
    return {"X-Auth-Token": state.get("token")}

def pull_alerts(ctx, since):
    resp = http.get(ctx.base_url + "/alerts", params = {"from": since, "limit": 200}, headers = _headers(ctx))
    levels = {"critical": "严重", "high": "高危", "medium": "中危"}
    return [{
        "id": item["uuid"],
        "time": item["occurred_at"],
        "severity": levels.get(item["level"], "低危"),
        "name": item["title"],
        "source_ip": item["src"],
        "destination_ip": item["dst"],
        "raw": item,
    } for item in resp.json()["items"]]

def block(ctx, target, duration):
    resp = http.post(ctx.base_url + "/blacklist", json = {"ip": target.ip, "expire": duration, "memo": ctx.task_id}, headers = _headers(ctx))
    if resp.status != 200:
        fail("设备拒绝：%d" % resp.status)
    return {"ok": resp.json()["code"] == 0, "rule_id": resp.json()["id"]}

def unblock(ctx, target, lease):
    resp = http.delete(ctx.base_url + "/blacklist/" + lease.rule_id, headers = _headers(ctx))
    return resp.status in [200, 404]

def verify(ctx, target, lease):
    resp = http.get(ctx.base_url + "/blacklist/" + lease.rule_id, headers = _headers(ctx))
    return resp.status == 200
```

脚本只能用平台提供的这些函数：

| 函数 | 作用 |
| --- | --- |
| `http.get`、`http.post`、`http.put`、`http.delete` | 访问插件登记过的设备地址 |
| `secret.get` | 按名称取凭据；值不会出现在日志里 |
| `state.get`、`state.set` | 每个插件自己的小型键值存储，用来放令牌和拉取位置，可设过期时间 |
| `json`、`base64`、`hash.sha256`、`hash.hmac_sha256` | 编码与签名 |
| `time.now`、`log.info`、`log.warn`、`fail` | 时间、日志、中止并报错 |

## 5. 运行与隔离

脚本语言选 Starlark：语法接近 Python，学习成本低；语言本身没有文件、进程和网络能力，所有对外访问只能通过平台给的函数。解释器用 Go 实现，直接编进采集器，不需要另装 Python 运行环境。

| 限制 | 做法 |
| --- | --- |
| 能访问哪里 | 只能访问插件登记的设备地址；域名解析后再核对 IP，跳转到登记范围之外的请求拒绝 |
| 跑多久 | 每次调用有步数上限和超时，超出即中止 |
| 用多少内存 | 插件在独立的工作进程里运行，由操作系统限额；解释器自身不限制内存 |
| 并发与速率 | 每个插件有并发数和每分钟请求数上限，防止把设备打挂 |
| 响应大小 | 单次响应有上限，超出按失败处理 |
| 凭据 | 只存在采集器本地，脚本按名称引用；平台和 AI 都拿不到明文 |
| 传输 | 默认校验设备证书；自签证书需要登记指纹或 CA |

步数上限和中止分别使用解释器的 `Thread.SetMaxExecutionSteps` 和 `Thread.Cancel`。Starlark 的设计目标是程序短小、没有外部副作用，语言本身没有随机数和时钟这类不确定来源（时间由平台函数提供），递归默认是错误。见 [Starlark 语言规范](https://github.com/google/starlark-go/blob/master/doc/spec.md)、[Go 实现的接口文档](https://pkg.go.dev/go.starlark.net/starlark)。具体版本在实现时锁定并写入[依赖版本与部署清单](依赖版本与部署清单.md)。

需要浏览器登录的设备不在本设计范围内，仍按[响应联动与插件调研](research/响应联动与插件调研.md)里的独立进程方案另行评估。

## 6. 从草稿到启用

```mermaid
flowchart LR
    A[草稿] --> B[试运行]
    B -->|通过| C[签名]
    B -->|失败| A
    C --> D[下发到采集器]
    D --> E[启用]
    E --> F[停用或回退上一版本]
```

1. **试运行**分三档，依次通过才能签名：
   - 模拟设备：用样例请求和响应回放，不出网，检查语法、字段映射和成功条件。
   - 真实设备只读：只执行 `health`、`pull_alerts`、`verify`。
   - 真实设备测试封禁：对保留测试地址封禁 60 秒，依次执行封禁、回读、解封、再回读。
2. **签名**：平台对插件内容的摘要签名，版本一经签名不可修改；改动产生新版本。
3. **下发**：采集器只加载签名有效、且指定给自己的版本。
4. **回退**：重新启用上一个已签名版本，不需要重新试运行。

每次调用都记录入口、耗时、结果和脱敏后的请求摘要，页面上可以按插件查看最近的执行情况。

## 7. AI 生成插件

1. 用户选择设备类型和需要的能力，贴入接口文档的相关段落。
2. AI 给出草稿：能用模板表达就生成模板，否则生成脚本；同时生成一组样例请求和响应，供模拟设备试运行使用。
3. 用户审阅、修改，按第 6 节试运行。

约束：AI 只看到用户贴的文档文本，接触不到凭据和真实设备；生成的内容与手写的一样，要经过人工审阅、试运行和签名才能下发，没有捷径。生成记录保留所用模型和输入摘要。

## 8. 执行可靠性

插件只负责“怎么调设备”。授权、限时、幂等、到期解除和结果核对仍由平台和采集器的任务机制负责，规则不变：

- 每个动作带任务标识，设备支持时写进规则备注，重复下发不重复生效。
- 封禁都有期限，到期由采集器调用 `unblock` 并用 `verify` 确认。
- 设备没有明确答复时记为“结果未知”，先 `verify` 再决定重试，不直接重发。
- 保护名单内的地址在下发前就被拦下，插件不会被调用。

`pull_alerts` 默认每 60 秒执行一次，按设备告警标识去重，单次拉取有条数上限；设备不可达时退避重试并在页面上显示。

## 9. 页面

“响应中心 → 联动设备 → 联动插件”：一张插件表（编号、名称、写法、适配设备、能力、运行采集器、状态、最近执行），新建与编辑用弹窗，弹窗内包含源码、配置项、试运行日志和“签名并下发”。AI 生成是同一页上的另一个入口。插件和联动设备一样是按条目管理的对象，留在响应中心，不放进系统设置。原型见 `prototype/src/views/PluginsView.vue`。

## 10. 验收要点

1. 模板和脚本各完成一个真实设备的封禁、回读、解封全流程。
2. 隔离有效：访问未登记地址、超步数、超时、超大响应、读取凭据明文，全部被拒绝并有记录。
3. 未签名、签名不匹配、指定给其他采集器的版本不会被加载。
4. 设备超时或返回不明确时进入“结果未知”，不会重复封禁。
5. 拉取告警不重复、不遗漏，设备中断恢复后从上次位置继续。
6. AI 生成的草稿不经试运行和签名无法下发。
