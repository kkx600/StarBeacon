# 星烽 StarBeacon 采集器程序维护

采集器程序维护由现场部署管理员执行，与采集器 Web 管理账号、平台账号、设备注册和规则发布授权分别管理。当前入口为采集器 ZIP 内 `bin/starbeacon-agent maintenance`，支持独立发布密钥、离线 Agent 制品校验、程序切换、前版本回退和中断恢复。主机服务使用 systemd，容器使用独立 Docker 实例；Go 服务不接收任意 shell，不持有 Docker socket。

本流程只切换 Agent 程序及所随附的静态文件。检测引擎、系统镜像、驱动、插件、管理网络、平台灰度及制品在线订阅不属于此入口。专属容器内的原生 systemd 服务已验证程序安装、切换和回退；完整宿主安装、捕获／规则健康、生产镜像及跨版本数据兼容仍需分别验收。本机 `/readyz` 不证明平台持久接收、镜像质量或实际封禁效果。切换期间有采集间隙，不能称为无损升级。工程状态见[功能实现与验收状态](功能实现与验收状态.md)。

## 信任与制品

发布签名使用独立 Ed25519 密钥，签名域为 `StarBeacon/collector.release.v1`，不能使用设备命令、mTLS 或注册凭据替代。公钥由部署管理员在设备配置中固定；私钥保留在离线发布环境，不能放入采集器、业务数据目录或发行 ZIP。

```sh
./bin/starbeacon-agent maintenance keys --key-dir /secure/starbeacon-release
./bin/starbeacon-agent maintenance sign \
  --archive /artifacts/starbeacon-collector-v0.1.0-linux-amd64.zip \
  --key /secure/starbeacon-release/release.key \
  --generation 1 --version v0.1.0 --arch amd64 --commit <完整提交SHA> \
  > /artifacts/collector-proof.json
```

签名固定版本、源码提交、Linux 架构、ZIP 摘要与长度、发布代次、数据格式和授权时间。签发默认有效七天，最大允许三十天。代次必须严格递增；显式回退不降低已见代次，不能通过再次安装旧授权绕过回退流程。已安装、已核验的前版本可在其原签发授权过期后恢复，仍须核对本机保存的程序摘要。

ZIP 在服务停止前复制到管理员私有校验快照，摘要与解包读取同一份快照；外部源文件改写不影响已校验字节。限制压缩体积 256 MiB、解压体积 512 MiB、单文件 128 MiB 和 20,000 个条目，来源清单最多 2 MiB。越界、重复、符号链接、设备文件、路径冲突、非目标 ELF、程序摘要／长度和版本身份不一致均拒绝。解压通过 Go `os.Root` 约束在独立暂存目录内；不执行包内脚本。磁盘至少保留压缩快照、解压空间及 64 MiB 维护余量；快照在本次校验结束后清除。正式发行还须经过已有 ZIP、UPX、SBOM、许可、同源提交与发布门禁，维护验签不能替代这些条件。

## 部署目录与配置

程序、业务数据和运行配置必须使用三个独立绝对目录。程序目录、部署配置、发布公钥和环境文件由部署管理员控制，禁止组／其他用户写入。业务目录预先属于非 root 服务 UID／GID，推荐 `0700`；维护工具不递归更改存量目录权限或重建身份。

下面是容器部署配置示例；对应镜像必须预先导入并按实际不可变摘要替换。

```json
{
  "schema_version": 1,
  "instance": "site_a",
  "mode": "docker",
  "root": "/opt/starbeacon/collector/site_a",
  "data_dir": "/var/lib/starbeacon/collector/site_a",
  "config_dir": "/etc/starbeacon/collector/site_a",
  "public_key": "/etc/starbeacon-release/release.pub",
  "uid": 10001,
  "gid": 10001,
  "ready_url": "https://127.0.0.1:28081/readyz",
  "ready_ca": "/etc/starbeacon/collector/site_a/ca.crt",
  "retention_days": 180,
  "docker_image": "registry.example/collector-runtime@sha256:<实际镜像摘要>",
  "docker_network": "collector_site_a"
}
```

部署配置默认保留期为 180 天，可设置 1–3650 天，仅影响随后创建的维护记录及暂存制品。记录与制品分别冻结保留截止，修改配置不重算既有期限。到期材料由部署管理员执行维护回收，当前及前版本、中断恢复材料和有效回执引用继续受保护；保留期到达不等于允许删除正在使用的程序。数据保留和配置缓存分别遵循[留存设计](数据留存与生命周期设计.md)。

`config_dir/agent.env` 使用共同的无展开格式 `SB_键=字面值`，不接受重复键、引号、空白或 shell／环境变量展开。必须明确 `SB_MODE=production`、数据目录内的 `SB_STATE_PATH=<data_dir>/agent.db` 以及 `SB_LOCAL_PASSWORD_FILE`；密码不能通过命令参数传入。TLS、设备身份、平台地址和规则配置遵循[工程运行配置](工程实现与开发.md)。CA、证书、命令公钥和密码文件须对实际服务用户可读，私钥与密码保持受限权限。运行路径、账号、镜像、网络、环境文件摘要和维护身份在持久状态中绑定；更换部署方式或目录不能作为同一次程序升级。

容器配置必须显式选择网络，默认示例不使用宿主网络；`host` 仅用于已经规划并验证的 Linux 采集环境。本工具不创建／修改管理 IP、网卡、路由、宿主网络或镜像端口，不接管其它容器网络命名空间。多接口、隔离策略、Suricata 与离线原生执行依赖须按目标运行镜像分别落实，不由启动 API 就绪推定可用。

主机模式设置 `mode=systemd`，移除两个 `docker_` 字段。服务 UID／GID 必须在本机账号目录中实际存在；目录、凭据、检测依赖及前端反向代理由部署管理员预先配置。静态资源代理指向 `<root>/current/www`，配置同源路由、TLS 和缓存规则；CLI 不接管代理配置，也不把程序就绪视为前端升级已经验收。没有通用默认密码和自动接管现有实例的安装行为。服务模板可用以下命令生成，再以同一实例名安装至 `/etc/systemd/system/starbeacon-agent-site_a.service`，执行 `systemctl daemon-reload`。不将专属容器内的服务验证视为所有 Linux 发行版的安装资格。

```sh
./bin/starbeacon-agent maintenance render-unit \
  --config /etc/starbeacon/collector/site_a/deployment.json
```

模板使用非 root 用户、仅 `NET_RAW` 的环境能力和边界、`NoNewPrivileges`、只读系统、独立临时目录、明确业务写目录、512 任务上限及整组退出。首次安装不能接管已运行但没有受管状态的同名主机服务。具体能力语义见 [systemd 服务执行约束](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)。

## 切换、回退与恢复

```sh
./bin/starbeacon-agent maintenance status --config /etc/starbeacon/collector/site_a/deployment.json
./bin/starbeacon-agent maintenance apply \
  --config /etc/starbeacon/collector/site_a/deployment.json \
  --archive /artifacts/starbeacon-collector-v0.1.0-linux-amd64.zip \
  --proof /artifacts/collector-proof.json \
  --request-id maintenance_site_a_001 --expected-revision 0
```

每次维护使用独立请求标识和期望修订。重复相同请求返回原回执，不重复重启；同键不同制品或授权参数拒绝。状态查询读取原子快照，可在维护写锁持有期间读取；其它维护写入拒绝并发。更新不覆盖已安装的同名版本目录。

执行顺序为：验证部署与当前状态 → 验签／解包 → 持久保存目标、原版本与阶段 → 确认原进程退出 → 只读核对 WAL 与未决责任 → 原子切换 `current` → 启动 → 核对实际程序及显式 CA 的 HTTPS 就绪 → 提交修订与回执。

WAL 必须具备正确身份、代次、事件目录及待传计数。未完成规则事务、执行中任务、没有独立核实依据的未知任务、未确认解除或到期的租约都会拒绝切换。核实过的规则中断记录必须关联同设备的独立成功核实任务和回执，不接受仅填入一个“已核实”标记。检查复用实际采集器任务和租约契约，不改写数据；拒绝后恢复原程序，不将本机时钟到期当成设备已经解封。

新程序启动或健康检查失败时，用独立于原调用取消的恢复期限停止目标，选择已保存前版本，再核对其实际程序和 HTTPS 就绪。恢复失败保留 `unknown`，禁止下一项维护覆盖依据。journal 使用同步写入和原子替换，服务退出、版本选择与就绪分别留证；发生主机断电或维护进程被强制结束时，启动守卫拒绝自行运行未确认目标，由现场管理员执行恢复：

```sh
./bin/starbeacon-agent maintenance recover --config /etc/starbeacon/collector/site_a/deployment.json
./bin/starbeacon-agent maintenance rollback \
  --config /etc/starbeacon/collector/site_a/deployment.json \
  --request-id maintenance_site_a_rollback --expected-revision <当前修订>
```

首次安装失败没有可恢复前版本时，仅撤销程序选择并保持数据，不编造一个可运行的原版本。维护准入检查在确认原进程停止后进行；发现未决责任时恢复原程序，期间仍存在管理间隙。持续响应的生产升级还需维护前排空和独立责任交接，不能将此检查视为全流程不中断资格。

当前只接收数据格式标识 1；不执行数据迁移、不复制／回滚 WAL，也不声称任意未来版本可回退。运行配置、证书和目录不得在维护期间由其它工具并发修改。

## 历史维护回收

回收入口与维护入口使用同一部署配置及排他锁，支持主机服务和容器部署。默认仅预览，实际回收需要显式传入 `--execute`：

```sh
./bin/starbeacon-agent maintenance cleanup \
  --config /etc/starbeacon/collector/site_a/deployment.json
./bin/starbeacon-agent maintenance cleanup \
  --config /etc/starbeacon/collector/site_a/deployment.json --execute
```

回收不停止或启动服务，不访问 Docker socket、设备接口或业务 WAL，不调整维护修订和发布代次。输出包含观测时间、候选、保护目录、实际删除数量、逻辑文件字节和剩余候选标记；逻辑文件字节不等于物理磁盘即时释放量。此命令由部署管理员调用，可纳入其维护调度；采集器在线服务不取得管理员回收权限。

| 对象 | 回收边界 |
| --- | --- |
| 当前及前版本 | 持续保护，过期也保留可运行与回退依据 |
| 未完成／未知维护 | 拒绝整轮回收，先恢复及核对实际运行状态 |
| 有效维护回执 | 其引用的目标、原版本与历史快照均保持保护 |
| 到期历史制品 | 核对独立冻结期限、来源、管理员归属、文件类型、同文件系统及体积后回收 |
| 旧格式制品 | 仅使用可核对的历史回执作为来源；没有来源的目录保留并计为未托管，不按修改时间猜测到期 |
| 维护回执 | 仅回收到期且非当前维护的记录；旧格式制品未删除前保留其来源回执 |

每轮最多核对 4096 份维护回执和 1024 个制品目录，最多删除 100 份记录和 5 个制品。目录超过核对预算时在删除前拒绝；管理员须先核对异常容量。单制品采用分批目录读取，最多核对 40,010 个文件／目录及 514 MiB 逻辑文件数据。链接、额外挂载、来源冲突、未知对象或可被其他账号改写的文件会阻止回收；异常不触发目录外清理。

制品回收先持久保存独立凭据，再将目录原子移入管理员专属 `reclaim/`。递归删除中断后，剩余文件仍由独立凭据绑定，后续调用继续处理；已删除目录但尚未提交凭据的情况不会重复计量。回收未完成时，同名制品不能重新暂存。失败轮次可能已移动目录或删除部分文件，已完成计数为零不代表没有副作用；未完成责任由独立凭据保留。当前状态、业务身份与 WAL 均不随回收回滚。该流程不等同全域保全、备份销毁或生产存储容量资格。

## 容器权限与验收边界

容器使用固定镜像摘要、`init`、只读根、512 PID、4 GiB 内存上限、限定临时目录及本地日志轮转。只挂载本部署的程序／配置只读目录和业务数据写目录，不挂载宿主根、Docker socket 或其它实例数据。镜像声明的额外匿名卷只读挂载，不得遮蔽受管路径；随所属容器回收。持久业务数据不得写入镜像匿名卷。同名容器必须具有当前实例的精确所有者标签；首次安装拒绝接管已有运行容器。

Docker 为非 root 用户配置 `cap_add: NET_RAW` 只保留边界集合，不能据此假定实际抓包权限生效。受信启动程序在容器内短暂使用 `NET_RAW`、`SETUID`、`SETGID` 和 `SETPCAP`，随后设置服务用户／组、清除附加组、移除其余边界能力，并通过环境能力把 `NET_RAW` 传递给实际 Agent。Agent 不具备 `SETUID`、`SETGID`、`SETPCAP`、`NET_ADMIN` 或 `SYS_ADMIN`，保持 `NoNewPrivileges`。独立启动程序不随普通 Agent 更新隐式替换，其自身更新需要单独部署验收。[Linux 能力与环境能力](https://man7.org/linux/man-pages/man7/capabilities.7.html)、[Docker init](https://docs.docker.com/reference/compose-file/services/#init)

专属验证脚本为 `tests/acceptance/collector_update.py`，按实际原生镜像与源码摘要构建两个 Agent，验证生产 HTTPS、既有 WAL 积压保留、重复请求、无效签名不中断、失败回退、强制中断后的启动拒绝、恢复及显式回退，同时核对配置摘要、数据文件身份、事件原字节、来源检查点、WAL 代次、实际 UID／GID、能力和隔离。既有 WAL 使用实际 EVE 读取器和固定试验路由构造；首次离线启动不推定已经完成平台注册或路由授权。权限单测还须在独立容器验证非 root `AF_PACKET` socket 与不能恢复 root；普通非 root Go 用例只验证拒绝路径。完整远程执行、原始失败和覆盖率按[测试记录](测试覆盖与验收记录.md)登记，不把脚本存在或模板生成视为实际通过。
