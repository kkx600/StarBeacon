# 星烽 StarBeacon 实施与容量规划

调研基准日：2026-09-28。适用于单组织、集团与多租户 SaaS，1–200+ 探针。以下容量、工期和性能指标是有明确假设的规划值，尚未通过 StarBeacon 实际压测；设备、规则、事件分布和保留要求确定后必须复算。

## 1. 采用顺序与成本原则

优先投入可复用的证据链、可靠接收、租户权限和告警工作台，然后交付模型、报告与 MCP。自动封禁需要真实数据评测、设备回读和到期撤销，在试点阶段先采用手动审批。

“性价比最高”应定义为达到同样检测和运营目标时，基础设施、模型、标注、运维与误处置总成本最低，不能用最新版本、模型参数量、GitHub 星标或 token 单价单独判断。方案按以下顺序压低成本：

1. 原始告警全量入 ES，协议日志分类留存，避免所有 EVE 类型都保存同样长的时间。
2. 默认保存必要 PCAP 证据，完整历史窗口依靠有限环形区，只有指定网络区开启全量归档。
3. 用关联与确定性规则减少需要模型反复分析的相同上下文，保留原始证据，不用删除告警获得降噪指标。
4. 模型按任务路由，小模型、通用模型与人工之间允许拒绝判断；闲置 GPU 不一定比托管调用便宜。
5. 合并业务部署，保留可扩展的进程边界；不因为有 200 个探针就自动要求 Kubernetes 或十几个微服务。

## 2. 容量输入表

正式报价与采购至少收集以下数据，探针数量只是其中一项。

| 输入 | 单位与说明 |
| --- | --- |
| 每探针平均／峰值带宽和包速 | bit/s、packet/s；高 PPS 小包与同带宽大包负载不同 |
| 事件种类及速率 | 告警、flow、DNS、HTTP、TLS、文件、统计分别计 EPS |
| 活跃流与应用计量 | 活跃流数、周期、聚合维度基数、明细范围；实时 flow EPS 可能远大于告警 EPS |
| 平均／P95 事件大小 | 原始 EVE、标准化文档和模型上下文分别测 |
| 规则及协议 | 规则数、启用模块、TLS 比例、stream depth、文件提取 |
| 数据保留 | 告警、协议、PCAP、报告、审计、案件保全分别定义 |
| 环形窗口／离线缓冲 | 探针可离线多久、告警前窗口需要多久 |
| 租户与交互负载 | 并发检索、聚合、导出、报告、MCP 和模型任务 |
| 故障与恢复 | 队列覆盖多久，备份 RPO，允许恢复多久 |
| AI 数据约束 | 是否允许出域、模型任务量、平均 token、人工复核量 |

首次试点至少采集一个完整业务周期，建议 7–14 天并覆盖业务高峰。网络 TAP／SPAN 配置错误、镜像带宽不足或链路丢包应先解决，不能通过平台增加 CPU 补救不存在的数据。

## 3. 计算公式

以下使用十进制 GB/TB，1 TB = 10¹² 字节。`E` 是持续 EPS，`B` 是平均事件字节，`F` 是实测索引系数，`D` 是天数，`r` 是额外副本数，`u` 是目标最高磁盘利用率。

```text
每日原始事件量 = EPS × 86400
每日原始字节 = EPS × 平均事件字节 × 86400
ES 所需磁盘 = Σ(E_i × B_i × 86400 × D_i × F_i) × (1+r) / u
队列磁盘 = 持续写入字节/秒 × 积压秒数 × 副本份数 / u + 突发储备
探针 WAL = 单探针峰值写入字节/秒 × 允许断网秒数 / u
PCAP 原始字节/日 = 实际捕获 bit/s ÷ 8 × 86400
PCAP 存储 = 原始字节/日 × 保留比例 × 保留天数 × 存储冗余系数 / 压缩比 / u
积压清空时间 = 积压事件数 / (恢复后消费 EPS − 持续进入 EPS)
```

队列和 WAL 需额外覆盖消息头、索引、日志段和写放大；ES 预算必须分别计算原始事实、完整检索投影、研判和汇总，再加重建、合并与故障恢复空间。TLS 数据通常不能依赖高压缩率做预算，首轮保守采用压缩比 1。

例如 1,000 EPS、每条 3,000 字节、30 天、索引系数 1.3、1 副本、70% 利用率，需要约 **28.9 TB** ES 磁盘。若只有告警保存 30 天、短期协议数据更小且只保存 7 天，成本可能明显不同。不能把平均事件大小和所有保留期合成一个未经测量的常数。

持续 **1 Gbit/s 全量 PCAP = 10.8 TB/日**；保存 7 天就是 75.6 TB 原始字节，尚未计算冗余与空闲空间。200 个低流量探针可能比一个高速出口探针消耗更少存储。

## 4. 三档容量示例

为了使三种部署可比较，本表假设：原始告警平均 3 KB、保留 30 天；完整 `alert-search` 投影另计平均 1 KB、保留 30 天；其他可保留上下文平均 1 KB、保留 7 天；ES 各数据集索引系数暂取 1.3、1 副本、70% 利用率；队列保存 72 小时持续原始事件、3 副本、70% 利用率。真实投影大小须测量，研判、审计、证据索引及重建余量还要另计。

| 输入／结果 | 小型示例 | 标准示例 | 规模化示例 |
| --- | ---: | ---: | ---: |
| 参考探针范围 | 1–5 | 5–50 | 50–200+ |
| 持续告警 EPS | 10 | 100 | 1,000 |
| 持续其他上下文 EPS | 90 | 900 | 9,000 |
| 总持续 EPS | 100 | 1,000 | 10,000 |
| 建议测试突发负载 | 300 EPS | 3,000 EPS | 30,000 EPS |
| ES 原始告警＋上下文计算磁盘 | 0.491 TB | 4.91 TB | 49.10 TB |
| ES 完整告警检索投影计算磁盘 | 0.096 TB | 0.963 TB | 9.63 TB |
| ES 上述三项计算合计 | **0.587 TB** | **5.87 TB** | **58.73 TB** |
| 队列计算磁盘总量 | 0.133 TB | 1.333 TB | 13.33 TB |
| 假设聚合捕获带宽 | 50 Mbit/s | 500 Mbit/s | 5 Gbit/s |
| 全量 PCAP 原始字节/日 | 0.54 TB | 5.4 TB | 54 TB |
| 假设留存 1% 证据、7 天的对象物理容量 | 0.081 TB | 0.810 TB | 8.10 TB |

PCAP 最后一行另外假设存储冗余系数 1.5、70% 利用率、无压缩。**1% 只是算例，不是告警包比例或实现保证。** 告警风暴、长连接或案件保全会显著增加保留量；应设置租户与网络区配额、证据包大小上限和超限提示。

应用流量功能必须另加计量数据：200 探针每 5 秒各输出 200 个聚合记录约 8,000 EPS，若平均 500 B、留存 1 天、同样 ES 参数约增加 1.28 TB。若每台 10,000 活跃流都每 5 秒上报，则为 400,000 EPS，同参数约 64.18 TB/日保留容量。默认采用完整本地计量、有界维度聚合、受限流明细；详细窗口、衍生汇总和额外队列磁盘不得遗漏。上述例子不与三档表中网络上下文盲目相加，应先确认是否已包含相同数据。[应用计量设计](应用识别与响应性能设计.md)

探针本地 WAL 独立计算：若某探针持续 100 EPS、平均 1.2 KB、要求离线 24 小时并预留至 70% 使用率，约需 14.8 GB，再加日志段开销及突发余量。PCAP 环形区独立磁盘预算，不与 WAL 无限制争用空间。

## 5. 部署拓扑与资源起点

下表只用于搭建压测环境，不作为采购单或吞吐保证。规模较小也可能有很高的抓包负载；CPU 需求需要用目标规则和真实包长验证。

| 场景 | 拓扑与资源起点 | 可用性边界 |
| --- | --- | --- |
| 功能验证／演示 | 1 台 16 vCPU、64 GB RAM、约 2 TB SSD 的平台主机，合并 API/Worker、PG、ES、Redis、队列；探针独立；对象存储单机；浏览器／回放限并发 | 无 HA，不承担生产 RPO/SLA；大模型优先远程调用 |
| 标准生产 | API/Worker 至少 2 实例；PG 主备可从各 8 vCPU／32 GB 测起；ES 3 个节点，各 16 vCPU／64 GB／4 TB NVMe；NATS 3 节点各约 1 TB 数据盘；Redis 主从及 Sentinel；独立对象存储 | 计算的 5.87 TB 之外保留分析、重建和故障空间；节点置于不同故障域 |
| 规模化生产 | API/ingest/worker 分池；ES 6–12 个数据节点、64–128 GB RAM、数据盘总量建议从 96 TB 级测试；NATS 3 节点各 8 TB；按热点拆数据单元；独立连接器／回放／模型池 | 58.73 TB 是给定假设下的三项容量，非完整采购量；用节点故障和恢复时间决定单元上限 |

功能验证可使用 ES 零额外副本和 NATS 单副本，与上一节按生产冗余计算的容量及可靠性不等价；配置必须明确标识验证用途。NATS 的严格落盘性能、ES 索引性能与对象存储写性能分别测，不能在同一块消费级磁盘上混跑后声称三者各自都有容量保障。PG 控制面资源按任务、对象清单和审计量估算，通常不按原始事件 EPS 等比例增长。

单探针可从 8–16 个物理／虚拟 CPU 核、16–32 GB 内存与独立缓存盘试测中等流量，但不能承诺任意规则下的 1/10 Gbit/s。验证 NIC、RSS、NUMA、抓包模式、包速、流重组和热更新内存；高带宽独立做传感器基准。

小型私有化使用可复现的容器或系统服务部署；标准生产可使用企业已有虚拟化／容器环境；已具备 Kubernetes 运维团队时再采用 Helm 与独立状态服务。PCAP 采集需要宿主机网络与明确权限，不把它当作普通无特权 Web 容器。

Redis 缓存组可从主从各 4 vCPU／8 GB、`maxmemory` 4 GB 测起，宿主还要给复制和进程留余量；协调组独立预算。生产三台 Sentinel 分散故障域，不能因为一个主从就宣称自动切换无损。Prometheus 可从 4 vCPU／8 GB／100 GB 试测，实际按序列数量、采样周期和保留天数估算；不默认引入全量追踪存储。客户 Runner 从 2–4 vCPU／4–8 GB 起，浏览器并发默认每实例 1、每 Runner 2，实测后开放。规则回放采用独立 8 vCPU／16 GB Worker 起点，CPU、内存和临时盘有硬限制，不能争用实时探针资源。

### 5.1 海量数据处理策略

| 环节 | 起始配置／方法 | 扩容与保护依据 |
| --- | --- | --- |
| 探针／gRPC | WAL、字节与条数双限组批、独立控制通道、压缩按 CPU 收益启用 | 捕获丢包与 WAL 最老年龄；不能只看连接数 |
| JetStream | 按数据单元、事件优先级与固定虚拟分区组织；消费者拉取、有限 in-flight | 用持续字节/s、积压年龄、落盘时延决定扩容；避免每探针一个复制 stream |
| 索引 Worker | Bulk 从 5–15 MiB 或 1,000–5,000 条上限测试，按最先到达条件刷新 | 分项检查；429 退避；映射失败隔离；并发以 ES 拒绝率和 GC 调整 |
| ES 刷新 | 从 2 秒测试，满足近实时目标后按索引角色调整 | 不对每条写入使用 refresh=true；`indexed` 与 `searchable` 分开计量 |
| ES 分片 | 目标主分片 10–50 GB；低量共享池按周／月，高量按日 | 按实际分区数据量定主分片数；严禁 200 探针×每天×多索引机械建分片 |
| 查询 | 必要的时间与租户过滤、PIT、游标、投影、汇总、导出队列 | 给大聚合、path 包含、导出和 MCP 独立并发预算，租户公平调度 |
| 关联／模型 | 按稳定键分区关联、合并相同证据快照、模型输入裁剪与预算 | 不以降低检测覆盖换成本；高优先研判与报告分队列 |
| 工作流／投影 | PG outbox 与分来源版本合并，批量状态更新异步完成 | 监控原始索引与投影水位；大范围操作不在 HTTP 请求内更新全集 |
| PCAP／样本 | 分片、范围读取、短期 ring、保全配额、独立解析池 | 带宽与字节量单独预算；不能按 EPS 推算 PCAP 容量 |
| 通知／Syslog | 独立队列、租户限流、通知聚合、持久发送水位 | 远端故障不阻塞告警入库，离线超窗明确记录缺口 |

分片算例：规模化原始告警 1,000 EPS × 3 KB × 86,400 × 1.3 ≈ 337 GB 主存储/日，可从每天 8 个主分片（约 42 GB/片）测试；检索投影约 112 GB/日，可从 3 个主分片测试；9,000 EPS × 1 KB 的网络上下文约 1.01 TB/日，可从 24 个主分片测试。30 天告警＋投影、7 天网络为约 996 个含一副本的分片，仅为此算例。分片总数、堆、查询扇出和恢复时间决定是否合并池、调整周期或拆单元，不能只按单片大小配置。

峰值压测至少覆盖持续基线、3 倍突发、单节点退出、离线探针同时补传、月报与导出同时运行。恢复消费吞吐必须大于持续进入吞吐；扩到两倍 Worker 不能假设吞吐一定翻倍。大租户的查询、模型、缓存与消息配额独立，热点 tenant 迁独立 cell，不无限扩大全局共享集群。

### 5.2 质量与成本共同验收

优化必须同时报告原始告警留存率、数据缺口、规则检测命中、模型误判、检索延迟与成本。检测规则阈值、HTTP body 上限、stream depth、PCAP 抽取范围、模型上下文裁剪都可能改变效果，修改时使用同一授权回归集比较。未经评测的采样不能用于“全部告警入 ES”；网络上下文采样必须注明字段与统计偏差。

除上表外，通知队列容量约为峰值聚合后消息/s × 平均字节 × 离线窗口；Syslog 容量按未过滤原始输出字节单列；规则样本对象、隔离回放临时盘、测试 EVE、AI 生成调用费、报告 PDF 浏览器池和审计保留都单独计量。两条队列订阅同一原始流可共享原始留存，但各自派生结果和投递日志不是零开销。

## 6. AI 选型与费用

### 6.1 候选方案

| 任务 | 建议起点 | 原因／上线条件 |
| --- | --- | --- |
| 权限、白名单、时间比较、动作范围 | Go 逻辑与 CEL | 确定性、可复现，无需模型推理 |
| 简单有限分类与升级路由 | Jev 与 Laya 并列基准；保留简单分类器基线 | 比较领域精度、覆盖率、中文、校准和总成本 |
| 证据解释与复杂关联 | 托管 `deepseek-flash` 或通过验证的通用模型 | 允许出域时按量使用，无常驻 GPU 成本 |
| 私有化对话与总结 | `Qwen/Qwen3.5-9B` 候选 | 小规模本地部署起点，量化后需重新验收 |
| 更高要求的本地通用研判 | `Qwen/Qwen3.8-27B` 候选 | 需要更多推理资源，不能用参数规模推定收益 |
| 核心资产和高业务影响动作 | 人工复核 + 确定性策略 | 验证不足时不追求自动化覆盖率 |

模型名称和当前可用性已通过[Qwen3.5-9B 模型卡](https://huggingface.co/Qwen/Qwen3.5-9B)、[Qwen3.8-27B 模型卡](https://huggingface.co/Qwen/Qwen3.8-27B)、[Jev 文档](https://docs.typesafe.ai/models)、[DeepSeek 文档](https://api-docs.deepseek.com/quick_start/pricing/)核实。它们是候选，不是已经完成 StarBeacon 安防评测后的排名。

本地 GPU 预算从权重、KV cache、上下文、批量和并发一起估算。9B BF16 权重粗算约 18 GB、27B 约 54 GB，只是按参数字节估算的下界，不能据此宣称 24 GB／64 GB 显存即可满足任意上下文和并发。量化减少权重空间，但会改变质量与兼容性，需使用实际推理镜像测量。

### 6.2 托管调用费算例

当前 Jev `jev-1.13.0` 输入为 0.042 美元／百万 token、输出免费。DeepSeek Flash 高峰未缓存输入为 0.30 美元／百万、输出为 1.20 美元／百万。此处是 2026-09-28 官方页面快照，用于计算，非长期采购报价。[Jev 定价](https://docs.typesafe.ai/models)；[DeepSeek 定价](https://api-docs.deepseek.com/quick_start/pricing/)

假设每天 100 万条原始告警，关联与规则之后有 2 万组需要模型；每组 Jev 输入 1,500 token，其中 5% 升级通用模型，每次输入 4,000、输出 800 token，按 30 天计算：

| 项目 | 计算 | 30 天费用 |
| --- | --- | ---: |
| Jev 决策 | 20,000 × 1,500 × 30 ÷ 10⁶ × 0.042 | $37.80 |
| Flash 升级研判 | 1,000 × 30 × (4,000 × 0.30 + 800 × 1.20) ÷ 10⁶ | $64.80 |
| 合计调用费 | 不含其他开销 | **$102.60** |
| 对照：2 万组均直接调用 Flash | 20,000 × 30 ×同一单次 token 费用 | $1,296.00 |

2% 进入模型与 5% 升级均为假设，不能以降低覆盖率来虚构节省。上述两种策略还必须达到相同质量门槛才能比较；混合方案若漏掉更多重要事件就不是合格替代。

费用尚未包含对话、日报／周报／月报、AI 规则生成与自动修复、重试、tokenizer 差异、工具检索、人工标注、SaaS 运营与基础设施。Laya 本地推理无上述托管 token 账单，但会产生机器、维护、校准和升级成本。报告可利用可用的低峰价格，但预算先按常规价格做。

### 6.3 自建与 API 的盈亏平衡

```text
月总成本 = 数据基础设施 + 对象存储及备份 + 传输/导出
         + 模型API + 本地推理机器 + 标注与复核 + 运维

本地每次有效判断成本 = (机器折旧或租金 + 电费 + 运维 + 训练校准)/有效判断数
API每次有效判断成本 = (实际调用费 + 重试 + 特征检索)/有效判断数
```

只有推理量稳定、机器利用率足够，或必须离线／不出域时，常驻本地推理才可能更合适。硬件、云资源和 MinIO 支持费用在地域、采购方式与部署明确后报价，不捏造统一人民币总价。

## 7. 性能、可靠性与模型验收

### 7.1 工程目标

以下建议作为标准生产档的初始目标，在固定硬件、规则、文档大小、查询集合与配额条件下验收；不作为任意 200 探针场景的保证。

| 指标 | 初始目标／验收方法 |
| --- | --- |
| 原始告警完整性 | 已 `ingest_accepted` 的合规告警在约定故障模型内最终全部入 ES，隔离与迟到项可逐项对账 |
| 重放唯一性 | 断线、ACK 丢失、跨日和规则升级回放不增加同一原始事件计数 |
| 索引可见延迟 | 稳态从平台接收到可搜索 P95 ≤ 5 秒；积压补传单列 |
| 常用列表查询 | 最近 24 小时、受限字段、标准分页，在约定 30 并发查询下 P95 ≤ 2 秒 |
| 聚合与长查询 | 单独定义基准；超限转异步作业，不保证所有历史查询均在 2 秒内 |
| 突发负载 | 3 倍持续 EPS、至少 15 分钟，不静默丢失已确认告警；结束后积压可收敛 |
| 持续稳定性 | 24 小时以上混合负载与关键故障注入，长稳测试覆盖至少一个保留／任务周期 |
| 告警容量保护 | 可选遥测或 AI 过载不能耗尽告警预留资源 |
| API 可用性 | 生产目标 99.9% 月可用性，按真实监测及约定边界统计 |
| 权限 | 网页、REST、MCP、任务、缓存、证据链接全部通过越权负向用例 |
| 响应 | 设备回执／实际生效／效果验证分开；重复任务不重复副作用；TTL 和撤销可靠 |
| 应用流量 | 5 秒计量，聚合进入大屏 P95 ≤10 秒；等待识别特征、未知／混合单列 |
| 实时自动封禁 | 指定网络与设备前提下，确定性快路径 P95 ≤8 秒，小模型 ≤15 秒，通用 LLM ≤60 秒作为初始资格目标；不代表已实测 |

例如持续 1,000 EPS 时积压 1 小时为 360 万事件，恢复后消费 3,000 EPS，则净消化 2,000 EPS，约 30 分钟清空。若只能消费 1,000 EPS，积压永远不会减少。

自动封禁时延以满足规则判定的相关流量到达至设备配置生效验证计量，告警可见和真实流量效果分别有时间戳；设备接单不是终点。主平台通过独立控制连接下发给采集器，由采集器访问设备。冷认证、人工审批、慢设备与补传不享受快路径资格，必须另报实际耗时。详细前提、时间定义和 P50/P95/P99 测法见[响应性能设计](应用识别与响应性能设计.md)。

### 7.2 模型门槛

首期先以相同证据对照确定性规则、简单分类器、Jev、Laya 与通用模型。每类告警分别评估精确率、召回率、校准、拒绝率、延迟和成本；按安全事件／攻击活动划分样本，近重复告警不能充当独立测试。

自动误报关闭可将“被自动关闭样本的正确性 95% 置信下界 ≥ 99.5%”作为讨论起点；关键资产默认仍复核。自动封禁可讨论更严格的场景级精确率下界，例如 99.9%，但证据、目标归属、白名单、动作撤销等硬条件必须另外全部通过。具体门槛由业务误处置损失确定，达不到就保持建议或人工审批。

若仅观察到零错误，按独立伯努利样本的粗略“3/n”上界，约 3,000 个独立样本才有机会把错误率的 95% 上界估到约 0.1%；这并不代表未来没有误封，更不适用于把同一攻击的 3,000 条重复日志当作独立样本。不能用几十个演示案例授予自动封禁资格。

模型升级、量化、提示模板改变、规则族变化和语言变化都触发重评估。人工抽检必须覆盖被自动抑制的事件，避免只评估模型愿意提交的高置信样本。

## 8. 备份与恢复目标

| 故障范围 | 设计目标 | 前提与限制 |
| --- | --- | --- |
| 单个 API／Worker 故障 | 自动重启和任务重领，业务通常无需人工恢复 | 幂等、租约、无单机权威状态 |
| 单个消息节点故障 | 严格持久化配置与测试范围内，已确认消息 RPO 为 0 | R3 健康仲裁、真实持久存储与正确故障域 |
| 单个 ES 节点故障 | 通过副本维持可用，降低吞吐；已接受队列可重放 | 副本健康、预留恢复空间 |
| PG 主节点故障 | 按主备方式制定；同步主备可追求已提交事务 RPO 0 | 不把异步复制默认当作无损 |
| PG 集群灾难 | 建议 WAL 归档验证后 RPO ≤ 15 分钟，标准档 RTO 约 1–4 小时 | 独立备份与密钥可恢复；实际演练后签署 |
| ES 集群灾难 | 日快照情况下最坏快照 RPO 约 24 小时；队列幸存且覆盖区间时可补齐已接受事件 | 队列也毁损时不能声称无损；标准档恢复目标 4–24 小时按带宽测 |
| 对象存储灾难 | 由独立备份／复制周期决定，初始按 24 小时预算 | 案件证据要求更高时单独配置同步保全与故障域 |

多地域复制和同一机房另一个桶不是同一等级的灾备。ES 约 59 TB 及附加数据集的恢复时间与网络吞吐直接相关，需要先做小样本、全量估算与实际恢复测试。对更严格的全平台 RPO 需增加跨故障域持久原始批次归档或复制，再将成本计入预算。

恢复流程先验证身份、配置和密钥，再恢复 PG 与存储，核对告警水位及对象目录，重放允许的事件，重建状态投影，最后对照设备实际封禁状态恢复动作管理。恢复历史数据库不能触发陈旧审批和命令重新执行。

## 9. 实施阶段与团队

建议团队为 3 名 Go 工程师、2 名前端工程师、1 名安全检测／数据工程师、1 名测试工程师、1 名平台运维工程师，并有产品与设计参与；模型训练深入后需要独立 ML 支持。若团队更小，应收缩并行功能，不能保持同样时间承诺。

| 阶段 | 参考时间 | 交付内容 | 退出条件 |
| --- | --- | --- | --- |
| 技术验证 | 第 1–2 周 | 真实 EVE、规则与 PCAP 样本；MinIO 生产选项；ES 容量；Jev/Laya 接入实验；契约冻结 | 关键边界和成本输入有证据，验证报告可复现 |
| 数据与业务基础 | 第 3–6 周 | 租户身份、探针注册、WAL/gRPC/队列、ES 标准化、原始告警列表 | 断网重放、跨租户负向测试通过 |
| 调查闭环 | 第 7–12 周 | 资产组／网段、检索投影、HEX、规则灰度、PCAP、事件、审计、首个 API 响应闭环 | 能完成告警到设备生效／到期撤销，证据和实际规则版本可追溯 |
| 智能与运营 | 第 13–20 周 | Jev/Laya/LLM、AI 规则生成与回放、对话、日周月报、MCP、五类通知、Syslog、大屏与监控 | 形成 P0 完整试点；明确自动策略资格；模型失败不影响基础运营 |
| 生产与 SaaS | 第 21–32 周 | 租户运营、配额、HA／灾备、真实自动阻断、浏览器认证插件、EDR、企业应用通知 | P1 完成用户需求生产范围，标准档压测、权限及设备矩阵验收 |
| 规模化与运营 | 第 33–40 周 | 200+ 探针与海量查询、热点隔离、数据单元迁移、连接器版本兼容强化 | 达成约定吞吐／保留／查询组合，形成规模化交付基线 |

按上述 8 人工程团队，约 5 个月形成完整试点、8 个月生产交付、10 个月验证规模化，属于范围估算而非工期承诺。设备控制台适配数量、测试环境、采购支持和模型质量对进度影响很大。P1 是本需求的生产交付范围，不能用仅有 P0 演示替代自动阻断、插件、租户隔离与故障恢复验收；高级图谱等 P2 能力不影响本次闭环成立。

应用产品识别、活跃流计量和应用大屏纳入交付范围后，同一团队预计还需 4–6 周，用于计量器、产品样本库、基数控制、抓包性能和设备响应时延验证；可以贯穿前述阶段并行，但若不增加专人，不将这一增量默认为零工期。综合预算约 6–6.5 个月试点、9–9.5 个月生产、11–11.5 个月规模验收；完整计划需按首批应用与设备数量排期。

## 10. 调研资料如何转化为验收材料

| 资料／项目 | 使用方式 | 边界 |
| --- | --- | --- |
| [Suricata-Verify](https://github.com/OISF/suricata-verify) | 学习规则输出验证，选择有使用权的 PCAP 构建回归集 | 引擎回归通过不代表业务低误报 |
| [Suricata-Update](https://docs.suricata.io/en/suricata-8.0.7/rule-management/suricata-update.html) | 规则源管理、ET Open 起点、定期同步与版本化 | 各规则源独立记录使用和再分发条款 |

| [MITRE ATT&CK 检测策略](https://attack.mitre.org/detectionstrategies/) | 关联检测策略、技术、所需证据和覆盖状态 | 有规则映射不代表实测覆盖，缺少数据源时标明盲区 |

| [UNSW-NB15](https://research.unsw.edu.au/projects/unsw-nb15-dataset) | 在适用授权范围内研究分类基线 | 官方页面明确学术研究用途授权，商业训练与交付需另核实 |
| 客户授权样本 | 最关键的误报、业务授权、攻击结果和环境校准 | 脱敏、权限、标签质量与训练权利单独管理 |

ATT&CK 数据模型当前已经演进到检测策略框架，导入时固定实际版本与对象类型，不用旧数据源表硬编码长期契约。[MITRE 数据模型](https://mitre-attack.github.io/attack-data-model/docs/principles/attack-detections/)

本次只读官方资料与公开仓库，没有下载并执行攻击样本、调用付费模型、创建云资源或测试真实网络封禁。正式 PoC 在授权隔离环境进行。

## 11. 上线前必须完成的故障演练

1. 探针进程退出、文件轮转、截断、重启、离线 24 小时和 WAL 空间耗尽。
2. PubAck 前后断线、ACK 丢失、分区令牌过期、跨天重放和 N/N-1 协议兼容。
3. JetStream 单节点故障与多节点断电恢复，分别验证保证范围，不用 kill 进程替代全部存储故障。
4. ES Bulk 部分成功、429、映射错误、只读水位、删除旧索引后的非法补录。
5. 对象上传完成但 PG 提交失败、ETag 不一致、分片遗留、保全与生命周期竞争。
6. 模型超时、预算耗尽、无效 JSON、错误引用、恶意载荷指令、跨租户检索和权限撤回。
7. 封禁执行超时、回执丢失、设备重启、重复动作、多个租约、到期解封失败与紧急停用。
8. 报告重复触发、跨月跨时区、迟到数据、日 distinct 数不可直接累加、模型总结不可用。
9. 从独立备份恢复 PG、ES、对象与密钥，核对历史动作不会再次执行。
10. Redis 故障转移与缓存击穿，鉴权或预算不确定时不能放行高风险操作。
11. 状态更新先于原始事实、投影乱序、人工覆盖与旧模型结果竞争，检索／计数／导出仍一致。
12. AI 生成规则语法合法但匹配过宽、HTTP Raw 合成样本、加密 PCAP、完整规则包冲突、热重载内存不足。
13. 客户 Runner 离线、认证失效、MFA、私有接口变更、插件更新但仍有活动封禁，撤销路径保持可用。
14. 通知服务商部分受理、超时后重发、限流、恶意 Webhook；Syslog 断线、缓冲满和外部无应用 ACK。

## 12. 决策记录与剩余业务输入

| 事项 | 本方案建议 | 何时需要最终定案 |
| --- | --- | --- |
| 单组织／集团／SaaS | 同一产品模型，默认租户，必要时独立数据单元 | 已覆盖用户要求，交付配置时选择 |
| “全部告警入 ES” | 所有原始告警保留到约定期限，模型不参与入库过滤 | 立项时确定在线与历史期限 |
| PG 的 CRUD 边界 | 配置、事件、审批、任务、对象清单和审计 | 数据模型评审时固定 |
| PCAP 策略 | 默认证据包，可选环形提取和全量归档 | 根据业务取证与存储预算选择 |
| MinIO 生产方式 | 保留 S3 接口，生产需受支持实现与交付许可 | 采购与部署前；社区归档状态不能忽略 |
| Jev/Laya | 可选适配，先离线对照与影子运行 | 样本与数据出域约束确定后 |
| 自动封禁 | 正式支持影子、审批、自动；按场景授予自动执行资格 | 校准、连接器撤销和策略验收后，符合条件直接执行 |
| 200+ 探针容量 | 以 EPS、字节、PCAP 和查询并发验收 | 完成客户试点测量后，不以探针数量单独签容量 |
| 第一个响应设备 | 优先选择客户已经使用且有可核对 API 的防火墙／网关 | PoC 前明确品牌、版本和测试范围 |
| 本地大模型 | Go 控制面外接独立推理运行时 | 明确不出域要求、GPU 与质量目标后 |

这些输入影响具体资源和交付配置，不妨碍按本文开始契约、可靠采集、租户权限和证据闭环开发。需要采购或改变既定数据库路线时再作显式业务决策。
