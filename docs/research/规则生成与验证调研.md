# 星烽 StarBeacon 规则生成与验证调研

核查日期：2026-09-28。引擎基线：Suricata 8.0.7。本文只记录官方文档和官方开源项目可核实的能力，以及据此提出的实现约束；未在当前工作区运行 Suricata、回放样本或完成性能压测。完整产品流程见[规则管理设计](../规则管理设计.md)。

## 1. 规则语义与协议边界

| 已核实能力 | StarBeacon 实现约束 | 官方依据 |
| --- | --- | --- |
| 规则由动作、协议／地址／端口／方向和选项组成；`http` 可表示 HTTP/1 或 HTTP/2，协议是否可用还取决于引擎配置 | 生成器必须绑定目标探针能力与配置摘要；不能仅凭语法名称推断目标探针支持 | [规则格式](https://docs.suricata.io/en/suricata-8.0.7/rules/intro.html) |
| `content` 匹配字节，二进制字节使用 `\|xx\|` 形式；PCRE 有额外检查成本 | 保留原始字节、编码和偏移；优先有限范围的内容匹配，正则表达式单独评审与压测 | [载荷关键字](https://docs.suricata.io/en/suricata-8.0.7/rules/payload-keywords.html) |
| HTTP 提供方法、URI、主机、请求体等专用缓冲区；标准缓冲区与 raw 缓冲区的规范化语义不同 | 原始字节和引擎解析结果同时展示；生成器必须解释选择哪个缓冲区，不能把 HTTP Raw 文本直接当全部 TCP 载荷 | [HTTP 关键字](https://docs.suricata.io/en/suricata-8.0.7/rules/http-keywords.html) |
| HTTP/2 事务与流标识有关，有帧类型、设置和头部名等专用关键字 | HTTP/1 正样本不证明 HTTP/2 覆盖；需要分别测试 HTTP/2 帧、头部压缩和多流场景 | [HTTP/2 关键字](https://docs.suricata.io/en/suricata-8.0.7/rules/http2-keywords.html) |
| Suricata 不提供加密业务流量的自动解密；TLS 提供可见握手字段检测 | 密文 PCAP 不能生成声称匹配 HTTPS 明文路径的可用规则；可生成可见 TLS 特征规则，并明确检测对象 | [加密流量配置](https://docs.suricata.io/en/suricata-8.0.7/configuration/suricata-yaml.html#encrypted-traffic)、[TLS 关键字](https://docs.suricata.io/en/suricata-8.0.7/rules/tls-keywords.html) |
| `flowbits` 等会话状态可构成多条规则之间的依赖 | 单条规则通过不代表规则组有效；保留依赖图，做完整组装和整包回归 | [流关键字](https://docs.suricata.io/en/suricata-8.0.7/rules/flow-keywords.html) |

HTTP 请求体能否被检查还受目标探针的请求体上限、流重组深度、解析器、流量完整度限制。上传了完整应用文本，不等于生产链路一定能观察到同样的明文和字节范围。平台将这些条件保存为规则的适用前提，由发布兼容性检查逐项核对。

## 2. 标识、版本与来源

Suricata `sid` 标识签名，`rev` 表示修订；同一 `gid` 内必须避免 SID 冲突。官方文档还提醒 Suricata-Update 的合并行为需考虑 SID 唯一性。平台因此在每份合成规则包内按 SID 做全局冲突检查，而非仅依赖 `gid` 隔离。[元数据关键字](https://docs.suricata.io/en/suricata-8.0.7/rules/meta.html)

本地自定义规则可使用 1000000–1999999 范围；这不意味着任意其他来源不会使用该范围。平台仍要登记已有本地规则并检测冲突，由 PostgreSQL 事务分配，模型不能随意发明 SID。多个租户可复用本地编号，但合并到同一引擎规则集时必须保证无冲突。[SID 分配登记](https://sidallocation.org/)

官方 Suricata-Update 提供来源更新及启用／禁用规则的处理方式。StarBeacon 可以借鉴其来源和覆盖配置模型，平台侧仍统一管理不可变来源快照、许可、合并结果与签名制品；生产探针不能同时运行另一套自动更新器争抢规则目录。[Suricata-Update](https://docs.suricata.io/en/suricata-8.0.7/rule-management/suricata-update.html)

## 3. 校验、回放和性能

| 检查层 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 静态结构与平台策略检查 | SID／修订／依赖／允许动作／可疑高成本结构符合平台要求 | 实际引擎一定能加载 |
| 同版本引擎 `-T` | 目标配置和规则装载检查成功 | 命中样本、低误报、可承载目标带宽 |
| 隔离进程 `-r` 回放 | 指定样本、配置与版本下产生预期事件 | 真实生产流量全部覆盖、在线丢包为零 |
| 候选集与完整规则包回归 | 候选及依赖、现有规则集共同工作的结果 | 未测试环境的效果 |
| 专用 profiling 与生产构建性能对比 | 当前测试场景下的规则开销和资源增量 | 任意 CPU／网卡／带宽下的固定吞吐量 |

命令行正式提供 `-T`、`-r`、`-S`、`--init-errors-fatal` 和 `--strict-rule-keywords`；其中 `-S` 只加载指定规则，`-s` 会追加到配置规则。测试服务需保存准确 argv、配置和制品摘要，禁止用外部输入拼接 Shell。[命令行选项](https://docs.suricata.io/en/suricata-8.0.7/command-line-options.html)

OISF 的 Suricata-Verify 使用 PCAP、规则、配置和断言描述来验证输出，支持按引擎版本与特性限定样本。它适合作为测试契约的参考及研发回归工具。StarBeacon 自身的 Go 作业服务可执行固定引擎进程并验证 EVE JSON，不必把 Python 测试框架作为所有生产节点的依赖。外部上传的测试描述不能执行框架中的任意 Shell 钩子。[Suricata-Verify](https://github.com/OISF/suricata-verify)

`fast_pattern` 的选择影响预过滤；最长内容并不自动等于业务上最有区分力的特征。规则生成器应提供选择依据，再使用同一数据集实测。[Fast Pattern 选择](https://docs.suricata.io/en/suricata-8.0.7/rules/fast-pattern-explained.html)

规则 profiling 提供检查次数、匹配次数和 CPU tick 统计；匹配数不一定等于告警数，因为阈值和抑制可能影响输出。仅规则 profiling 需要相应编译能力，可通过 Unix socket 启停与导出。[性能报告](https://docs.suricata.io/en/suricata-8.0.7/performance/rule-profiling.html)、[按需 profiling](https://docs.suricata.io/en/suricata-8.0.7/rule-management/rule-profiling.html)

阈值关键字控制告警频率；`flowbits` 等状态动作仍可执行，IPS 中的 `drop`／`reject` 也不能理解成“达到告警阈值才阻断”。平台把检测、告警降噪和自动响应作为独立配置，测试同时检查事件数量和数据面行为。[阈值语义](https://docs.suricata.io/en/suricata-8.0.7/rules/thresholding.html)

## 4. 发布完成的证据

官方提供阻塞式 `reload-rules` 和非阻塞式 `ruleset-reload-nonblocking`。热重载会创建新的检测引擎再切换，期间额外占用内存；只重载规则相关配置，并不覆盖所有进程配置。[规则重载](https://docs.suricata.io/en/suricata-8.0.7/rule-management/rule-reload.html)

Unix socket 可查询最后重载时间、装载／失败规则数及失败清单。StarBeacon 应结合制品摘要、单写入者控制、引擎运行标识、重载完成及装载结果建立“已生效”回执。官方接口没有承诺返回完整内存规则集的加密摘要，不能仅查询一个规则数量就声称证明了精确版本。[Unix socket](https://docs.suricata.io/en/suricata-8.0.7/unix-socket.html)

平台规则在许可允许时加入发布元数据，并开启 EVE 的规则元数据输出。规则元数据可以用于告警的版本关联；实际接入须验证字段确实保留。源规则不允许改写或事件缺少元数据时，展示可用证据等级，不能用“读取日志时的当前版本”冒充事件产生时版本。[EVE 格式](https://docs.suricata.io/en/suricata-8.0.7/output/eve/eve-json-format.html)

## 5. 实施结论

StarBeacon 采用“自然语言／证据输入 → 受约束候选生成 → 固定引擎验证 → 正负样本回归 → 性能门槛 → 签名制品 → 授权灰度 → 生效对账”的闭环。AI 一键生成包括自动验证与修复预算，输出可审阅的规则和测试报告。发布是独立权限；已批准的发布策略可以自动推进灰度，未授权范围不能自动扩大。

规则不是入侵结果的充分证明。匹配请求只能支持“出现了某种请求行为”；攻击成功、资产受控和是否封禁仍需其他证据与响应策略。生成任务必须显式输出观测限制、未覆盖情况和待补样本，允许状态为“证据不足”，而不是强制输出一条看似可用的规则。
