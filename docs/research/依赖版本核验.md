Redis 8 采用 RSALv2、SSPLv1、AGPLv3 三选一许可；不能在发行清单中继续写成旧版本的 BSD 许可。go-redis 为 BSD-2-Clause。发行时登记实际采用的许可及第三方通知。[Redis 许可](https://github.com/redis/redis/blob/8.10.2/LICENSE.txt)、[go-redis 许可](https://github.com/redis/go-redis/blob/v9.22.0/LICENSE)。

StarBeacon 的设计选择：Redis 不保存告警事实，不承担持久消息队列，也不作为自动阻断授权、永久幂等记录或审计记录的唯一来源。NATS 承担持久消息传递；PostgreSQL 保存执行授权与动作记录。缓存键必须包含租户及权限版本，设置 TTL、大小上限和内存预算。缓存与不可随意驱逐的协调数据分开实例配置，不能靠不同逻辑数据库取得内存隔离。阻断锁最终由 PostgreSQL 约束及执行记录保证。缓存故障时降低查询加速能力；权限、额度、阻断授权不能因缓存故障而自动放行。

go-redis v9.22.0 的客户端缓存和自动流水线在发布说明中标为实验特性，首期不默认打开。普通 pipeline、连接池、上下文超时和有界重试应在压测中配置；不能把客户端默认超时当成全平台统一超时。[go-redis 发布说明](https://github.com/redis/go-redis/releases/tag/v9.22.0)。

## 五、交付锁定与验证边界

StarBeacon 自身 Go 编译器按用户要求固定 **1.26.0**；CI 设置 `GOTOOLCHAIN=local`，检查 `go.mod/go.sum` 中直接和间接依赖的最低 Go 版本，防止自动下载新工具链。上文已检查的 Go 模块直接下限可满足要求，完整依赖图与目标平台的构建兼容性仍要在项目代码和锁文件形成后验证。

版本基线不使用 `latest` 容器标签或 npm 的浮动主版本。交付记录应包含：服务版本、配置 schema 版本、镜像 digest、CPU 架构、操作系统基线、依赖锁文件摘要、SBOM、数据库迁移号和回滚兼容范围。应用回滚不自动回滚 PostgreSQL 数据迁移或 Elasticsearch 映射；数据库升级和索引迁移必须分别设计恢复路径。

这些是工程交付规则，不是已经执行的构建记录。正式发布前的必要验证是：Go 1.26.0 全量编译、Vue 模板类型检查、前端构建、三类部署拓扑的集成测试，以及真实流量与海量检索负载测试。没有通过这些检查前，应称为“固定选型基线”，不能称为“已验证的生产组合”。

Docker 的下层运行环境是实际依赖，不能从部署清单中遗漏：官方 APT 将 containerd 和 runc 作为 `containerd.io` 包提供，不能再与发行版的同名运行时混装。本次 Docker Noble stable 仓库可核实 `containerd.io_2.3.6-1~ubuntu.24.04~noble_amd64.deb`，以及 `docker-compose-plugin_5.5.1-1~ubuntu.24.04~noble_amd64.deb`。APT 交付方案固定这两个包版本；runc 采用该 containerd.io 包内的版本，验收记录 `runc --version` 和包摘要，不独立引入第二份 runc。Docker 29.8.1 的静态二进制包发行说明所带 containerd 为 2.3.5；它与上述 APT 打包方式不同，不能把两者的下层依赖信息混写。[官方 Noble stable 包目录](https://download.docker.com/linux/ubuntu/dists/noble/pool/stable/amd64/)、[Docker 依赖打包说明](https://docs.docker.com/engine/install/ubuntu/)、[静态包发行说明](https://docs.docker.com/engine/release-notes/29/)。

最小 PoC 使用已构建的应用镜像，不要求在部署主机执行镜像构建。Docker 与 Compose 是此部署档位的选择；正式环境可以使用客户现有容器平台或受管数据库，不为实现平台功能强制建设 Kubernetes。Suricata 生产探针优先直接运行在 Linux 主机或经过验证的专用容器配置中；镜像流量接口、网卡队列、抓包权限、磁盘和 NUMA 必须分别验收，不能把普通业务容器的网络配置直接当成探针配置。

Docker Engine/Moby 与 Compose 的项目许可证均为 Apache-2.0；Docker Desktop 不是本方案的服务器依赖，不能把其许可条款与 Engine 项目许可证混为一项。Ubuntu 是多个软件包构成的发行版，许可随具体包登记，不能统一写作 MIT 或 Apache-2.0。[Moby LICENSE](https://github.com/moby/moby/blob/docker-v29.8.1/LICENSE)、[Compose LICENSE](https://github.com/docker/compose/blob/v5.5.1/LICENSE)、[Ubuntu 包目录](https://packages.ubuntu.com/)。本文记录官方许可声明与产品发行边界，不对具体交付模式作法律判定。

依据：[protoc 36.2 发布](https://github.com/protocolbuffers/protobuf/releases/tag/v36.2)、[Go Protobuf 1.36.12 发布](https://github.com/protocolbuffers/protobuf-go/releases/tag/v1.36.12)、[Go Protobuf go.mod](https://github.com/protocolbuffers/protobuf-go/blob/v1.36.12/go.mod)、[gRPC 插件独立发布](https://github.com/grpc/grpc-go/releases/tag/cmd/protoc-gen-go-grpc/v1.6.2)、[插件 go.mod](https://github.com/grpc/grpc-go/blob/cmd/protoc-gen-go-grpc/v1.6.2/cmd/protoc-gen-go-grpc/go.mod)、[gRPC 1.84.0 发布](https://github.com/grpc/grpc-go/releases/tag/v1.84.0)、[gRPC go.mod](https://github.com/grpc/grpc-go/blob/v1.84.0/go.mod)。

安装版本表达分别为 `google.golang.org/protobuf/cmd/protoc-gen-go@v1.36.12` 与 `google.golang.org/grpc/cmd/protoc-gen-go-grpc@v1.6.2`，不能把 gRPC 运行时的 `v1.84.0` 填成生成插件版本。插件的仓库 tag 为 `cmd/protoc-gen-go-grpc/v1.6.2`，模块安装版本为 `v1.6.2`。这两种表达也不能混用。

Go Protobuf 官方建议生成器和运行时采用相同版本，因此两者均固定 1.36.12；gRPC 插件 1.6.2 生成源码要求 gRPC-Go 至少 1.64.0，选定的 1.84.0 满足此要求。这是源码声明的兼容范围，完整组合仍需用 Go 1.26.0 生成并编译验收。[Go Protobuf 兼容约定](https://github.com/protocolbuffers/protobuf-go/blob/v1.36.12/README.md#compatibility)、[gRPC 插件兼容常量](https://github.com/grpc/grpc-go/blob/cmd/protoc-gen-go-grpc/v1.6.2/cmd/protoc-gen-go-grpc/grpc.go)。

协议文件首期采用已有设计的 `syntax = "proto3"`，保留字段号和枚举号，删除字段进入 `reserved`，不复用旧编号。是否采用更新的 Editions 属于单独迁移项，不能仅因升级 `protoc` 而改变协议语义。CI 记录三种生成工具的 `--version`，重新生成后检查工作区差异，并测试新旧探针的双向兼容；生成代码提交仓库后不手工修改。Go 1.26.0 与 `GOTOOLCHAIN=local` 约束同时作用于应用和 Go 生成插件。
