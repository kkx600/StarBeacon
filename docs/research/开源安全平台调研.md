# 星烽 StarBeacon 开源安全平台调研

调研日期：2026-09-28。适用范围：个人与小型部署、集团多站点、SaaS 多租户，覆盖 1–200+ 探针。本文围绕 Go、Vue 3、Ant Design Vue、Suricata、gRPC、PostgreSQL、Elasticsearch 和 S3 兼容 PCAP 存储的既定方向，评估产品理念及复用边界。

“事实”指本次读取的官方仓库或文档内容；“设计推论”是针对星烽的建议。发布版本依据调研日 GitHub 官方 API 的 `releases/latest`，日期为 UTC；它是维护活动证据，不代表安全性、性能或生产成熟度认证。许可证按默认分支原文识别，不能由仓库徽标推导全部文件、依赖及商业功能的许可。

## 1. 结论与采用原则

星烽应围绕调查闭环建设产品：告警进入工作队列，关联资产与网络会话，获取证据，形成可追溯研判，执行处置并复核效果，最终进入事件报告与检测规则反馈。Security Onion 提供了连续调查路径，Arkime 提供了流量证据组织方式，IRIS 提供了事件协作对象；情报与自动化平台更适合作为独立连接器接入。

设计推论：一期保持一套 Go 控制面和一套 Vue 界面，自建告警工作台、资产上下文、规则生命周期、决策记录、动作执行与 MCP 权限入口。按业务需要接入成熟能力，避免同时安装多个完整 SOC、情报和 SOAR 平台，造成身份、存储、事件状态与运维重复。

## 3. 产品理念与可借鉴能力

### 3.1 Security Onion：围绕分析人员组织工具

事实：官方工作流将 Alerts、Hunt、PCAP、Cases 和 Detections 串联；网络侧包含 Suricata 检测、协议元数据和抓包，端点日志用于补足加密流量等可见性不足。[官方产品与工作流](https://docs.securityonion.net/en/3/main/introduction/)

事实：Onion AI 将供应商适配器与模型配置分离，并区分只读工具与修改工具的批准行为；MCP 当前文档明确列出事件查询和剧本查询，相关 API 属于 Pro 能力。[Onion AI](https://docs.securityonion.net/en/3/main/onion-ai/)、[MCP Server](https://docs.securityonion.net/en/3/main/mcp-server/)

设计推论：星烽告警详情应固定提供“关联事件、资产、网络会话、原始证据、研判、处置”入口；用户切换页面时保留租户、站点、时间窗和调查对象。规则命中后可进入对应规则的调优、版本和下发状态。复用产品交互理念，自建业务实现；不将整套发行版嵌入 Go 平台。

### 3.2 Wazuh：网络证据之外的主机上下文

事实：Wazuh 以端点 Agent 与管理端协作为核心，覆盖日志、文件完整性、软件清单和漏洞等数据；Active Response 支持一次性动作及到期撤销的有状态动作。[官方仓库](https://github.com/wazuh/wazuh)、[Active Response](https://documentation.wazuh.com/current/user-manual/capabilities/active-response/index.html)

设计推论：判断“攻击是否成功”应关联身份登录、进程、文件变更、服务状态和外联证据；单个 Suricata 规则命中只能证明检测条件满足。星烽预留 Wazuh、EDR、操作系统及应用日志连接器，后续按客户现有设施接入。封禁模型需要明确执行位置、有效期、撤销结果与失败原因；不需要为此整体复制 Wazuh 服务与索引器。

### 3.3 Arkime：会话索引与 PCAP 分层

事实：Arkime 支持横向扩展捕获节点和集中 Viewer；S3 Writer 支持 PCAP 分段上传、压缩、时间或大小切片，并可指向 MinIO。未完成上传的对象不能直接下载。[架构](https://arkime.com/architecture)、[S3 存储](https://arkime.com/s3)

设计推论：PCAP 模块应先查会话和对象索引，再提取所需证据，避免让页面扫描对象桶。元数据包含租户、探针、采集时间段、对象键、校验值及证据可用状态。探针保留短期本地环形缓冲，平台按保留策略归档，上传完成后才标记可获取。Arkime 可作为可选独立取证服务，经星烽统一鉴权访问；需验证双引擎采集开销及会话索引映射，不能假定与 Suricata 自动共用状态。

### 3.4 Malcolm：先丰富上下文，再呈现流量

事实：Malcolm 将 PCAP、Zeek 与 Suricata 数据汇集，进行地理位置、设备及资产上下文丰富，并通过 OpenSearch Dashboards 和 Arkime 分析。[官方概览](https://cisagov.github.io/Malcolm/docs/)

设计推论：星烽资产对象不能只有 IP。告警应显示业务系统、负责人、资产重要性、网络区、探针观测位置和协议服务，明确 IP 归属的生效时间。优先借鉴字段标准化、离线 PCAP 导入和数据丰富流程；整套引入 Malcolm 会带来另一组 OpenSearch、身份与分析界面，不符合星烽统一平台的初期成本目标。

### 3.5 MISP：可交换、可质疑的指标情报

事实：MISP 以事件、属性和对象表达情报，支持关联、分享控制及 API；其 warninglists 项目标记可能造成误报的常见指标，可在 API 层辅助过滤。[官方仓库](https://github.com/MISP/MISP)、[warninglists](https://github.com/MISP/misp-warninglists)

设计推论：一期情报中心优先接入 MISP API 或受信任的指标 Feed，保留来源、原始引用、共享范围、可信度、首次和末次观察时间、有效期与撤销状态。公共云、CDN、共享解析器等命中 warninglist 时产生解释与复核要求，而不是把 warninglist 当作绝对放行清单。情报命中参与研判评分，不直接等同入侵或封禁授权。代码许可与每个 Feed 的使用条款分别记录。

### 3.6 OpenCTI：保留知识之间的关系及出处

事实：OpenCTI 采用基于 STIX 2.1 的实体与关系模型；其目标包含保留信息原始来源、首次与末次出现时间及可信度。完整部署依赖搜索、缓存、消息与对象存储服务。[数据模型](https://docs.opencti.io/latest/usage/data-model/)、[官方仓库](https://github.com/OpenCTI-Platform/opencti)、[部署架构](https://docs.opencti.io/latest/deployment/overview/)

设计推论：星烽应区分“观察到的 IP/域名”等事实对象和“属于某攻击组织”等分析判断，记录判断来源。先实现指标与告警、资产、规则、事件的关系，保留 STIX 标识和外部引用；有持续情报运营团队后再接入 OpenCTI。早期无需复制完整知识图谱平台，也不能仅凭同一 IP 就推断攻击组织归属。

### 3.7 DFIR-IRIS：将调查变成可协作的事件

事实：IRIS 支持告警分配、创建或并入事件、选择导入的指标和资产；告警可解除事件关联而不被删除。默认分支 v3 为 Beta，官方仍将 v2.4.29 标为生产使用的稳定版本。[告警操作](https://docs.dfir-iris.org/latest/operations/alerts/)、[仓库版本说明](https://github.com/dfir-iris/iris-web)

设计推论：星烽“告警”和“安全事件”必须是不同对象。事件聚合多个告警，拥有负责人、任务、时间线、证据、处置记录、复盘和关闭原因。关联解除、告警关闭、误报标记分别建模。原始告警在 ES 保留，平台事务记录通过不可变 ID 关联，避免用户操作覆盖采集事实。IRIS 适合现有客户的事件系统连接器，不作为星烽界面的必需依赖。

### 3.8 TheHive：参考协作理念，避开归档基线

事实：TheHive 官方旧仓库明确说明 3.x、4.x 已停止维护和公开分发，并引导用户至商业版本文档。[旧仓库状态说明](https://github.com/TheHive-Project/TheHive)

设计推论：可以研究“告警升级为事件、分析器补充证据”的产品思路，但不选择归档代码作为新平台基础。客户已使用现行 TheHive 时，在确认其 API 与版本后提供双向连接器；星烽不依赖其旧数据模型或打包物。

### 3.9 Shuffle：连接器与执行记录构成自动化价值

事实：Shuffle 提供可视化工作流、OpenAPI 应用创建与组织管理，后端使用 Go；工作流将触发器、动作、条件和变量组织起来，并提供执行详情。[官方仓库](https://github.com/Shuffle/Shuffle)、[工作流文档源](https://github.com/Shuffle/shuffle-docs/blob/master/docs/workflows.md)

设计推论：星烽一期优先交付固定场景模板，例如“补充情报—生成研判—请求处置—核验结果”，每个动作具备输入输出、执行身份、凭据引用、超时、重试与幂等键。成熟连接器可通过 API 集成；不应因为后端同为 Go 就复制引擎。通用拖拽编排器安排在固定模板验证以后，以免先投入画布而缺少可靠执行。

### 3.10 Tracecat：智能体与确定性流程协作

事实：Tracecat 把智能体、工作流、事件、对话和 MCP 纳入同一产品，并使用 Temporal 运行持久化工作流。官方 README 将多租户、细粒度权限及敏感工具人工审批列于 EE 能力。[产品文档](https://docs.tracecat.com/overview/introduction)、[仓库及版本边界](https://github.com/TracecatHQ/tracecat)

设计推论：星烽的 LLM 负责生成候选判断、解释和查询计划；确定性策略决定是否允许动作，动作服务负责实际执行。自动化配置应包含租户范围、资产保护清单、条件、有效期、预算、失败策略与审计。可参考其“对话与事件共用工具”的方式自建 MCP；不把外部平台全部高级权限能力视为可直接取得的开源组件。

## 5. 统一产品闭环与规模适配

以下均为星烽设计推论。

1. **采集与可信性**：探针注册、身份校验、规则版本、时间同步、丢包率、积压和最后上报时间一同进入运行视图。数据缺失不能展示为“没有风险”。
2. **检测与聚合**：原始告警完整留存，展示层按规则、资产、来源、时间窗聚合；聚合不能销毁明细。告警、网络事件、处置记录使用不同对象类型。
3. **证据与研判**：每项结论关联 `event_id`、会话、PCAP 片段、规则版本、情报快照和资产上下文；输出“误报/真实威胁/待核实”与“尝试/疑似成功/确认成功/无法判断”两条独立维度。
4. **决策与执行**：模型建议、策略许可、实际执行和效果核验分别记录。封禁成功必须来自执行端回执；存在回执不等于业务风险已消除。限制动作范围并设置到期撤销和人工覆盖入口。
5. **事件与报告**：事件承接多告警调查；日报、周报、月报先固化统计口径、查询范围与数据水位，再生成自然语言。每个关键结论可跳回证据，记录编辑者与发布状态。
6. **反馈与评估**：误报原因沉淀为规则调优或场景知识，已确认样本进入版本化评测集；人工标注不能直接绕过审核进入模型训练或全局规则。

个人部署可使用同一代码库的合并部署方式，默认租户也保留租户标识。集团部署增加组织、站点、网络区域及委派权限；SaaS 增加独立租户身份、查询约束、对象存储隔离、凭据、模型预算和任务配额。集团汇总需要显式授权，不能以组织树替代租户边界。

从 1 台扩至 200+ 探针，应按总带宽、事件率、PCAP 保留期、查询并发和模型调用量分别扩容。采集入口、索引写入、取证作业、研判作业和报告作业需要独立背压与配额；不能用“支持 200 台”代替可测量容量指标。Arkime 的分布式捕获理念可供参考，但其公开架构说明不构成星烽容量承诺。[Arkime 部署架构](https://arkime.com/architecture)

## 6. 复用决策与落地验证

建议自建：统一身份和租户、探针控制面、ES 查询服务、资产上下文、告警与事件工作台、决策策略、动作执行、模型配置、报告和 MCP 入口。这些对象构成星烽的产品一致性。

建议可选集成：Arkime 取证、MISP 情报、OpenCTI 深度情报、Wazuh/EDR 主机数据、IRIS/TheHive 事件同步、Shuffle/Tracecat 工作流调用。每个集成必须经过适配器，使用平台内部标识、权限和审计，不让前端直接持有外部系统管理员凭据。

首轮验证围绕四项任务开展：同一告警能准确关联网络会话及 PCAP；中断后补传不会重复制造调查对象；一次动作可完整经历提交、执行、回执、撤销；单租户查询与模型工具不能读取其他租户证据。使用得到授权的正常与攻击样本回放验证误报和成功判定，保存规则、模型、提示词、输入证据与评测结果的版本。

当前研究确认了能力与依赖边界，尚未对这些平台进行部署压测、代码安全审计或连接器兼容性验证。开发基线应固定经过验证的 Release 与镜像摘要，避免把滚动文档、默认分支或 Beta 直接视为生产基线。
