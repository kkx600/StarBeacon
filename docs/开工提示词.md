# 星烽 StarBeacon 开工提示词

把提示词原样粘贴给对应的工具，就会按[开发任务](开发任务.md)一项一项往下做。前两段给 Claude 用，区别只是做完一项后停不停；交给 Grok 开发时用最后一节的提示词。

开工前确认两件事：远程主机 `home_dev` 可以连接；上一次的条目已经提交或已在开发任务里写明状态。

## 单项模式（做完一项就停，推荐）

```text
你在星烽 StarBeacon 仓库里工作。请完成 docs/开发任务.md 里的下一个条目，只做这一项。

1. 先读 AGENTS.md、docs/开发规范.md、docs/测试与发布流程.md、docs/开发任务.md；界面相关的条目再读 DESIGN.md。用 git status 核对仓库的实际状态，不要只信文档。
2. 从上往下取第一个还没完成的条目（编号只是名字，不代表先后；带 [~] 的条目先看“已做”和“剩余”）。先用几句话复述它的范围、涉及的文件和完成标准。条目标了“需确认”或者你发现范围有歧义时，先问我，不要自己定。
3. 动手实现。代码改动交给子代理完成，子代理的模型用 Opus 5.5：按开发规范第 8 节把这个条目的背景、范围、约束、完成标准和汇报格式写成一份完整的说明交给它；你自己只做决策、文档和复核，不直接改代码。子代理只改这个条目范围内的文件，范围外的问题记到开发任务的“待排期”。它汇报后，你要自己重跑关口一、抽查改动、能用浏览器时看一遍受影响的页面。
4. 验证。先过关口一（本机编译、静态检查、类型检查），再按测试与发布流程里的表做这个条目要求的关口二（远程）。失败就修到通过。远程连不上或条件不具备时，把条目标成 [!] 并写明原因，不要写成通过。
5. 更新 docs/开发任务.md：勾选条目，在进度记录里加一行，写清日期、结果、验证结论和提交号。
6. 提交。一个条目一个提交，说明用“<类型>: <中文说明>”。只在本地提交，不推送、不打标签，除非我明确说。
7. 汇报后停下：做了什么、验证结果（跑了哪些、没跑哪些）、遗留问题。等我说继续再做下一项。

全程用中文回复。测试只在远程执行，本机不跑 go test、vitest 和检查脚本。
```

## 连续模式（一项接一项，直到做完或卡住）

```text
你在星烽 StarBeacon 仓库里工作。请按 docs/开发任务.md 从上到下的顺序连续完成条目，每个条目都完整走完下面的步骤再开始下一个。

1. 先读 AGENTS.md、docs/开发规范.md、docs/测试与发布流程.md、docs/开发任务.md；界面相关的条目再读 DESIGN.md。用 git status 核对仓库的实际状态。
2. 从上往下取第一个还没完成的条目，复述范围、涉及的文件和完成标准。
3. 实现。代码改动交给子代理完成（模型用 Opus 5.5，说明写法见开发规范第 8 节），你只做决策、文档和复核。只改这个条目范围内的文件；范围外的问题记到“待排期”。子代理汇报后自己复核一遍。
4. 验证。先过关口一，再做这个条目要求的关口二。失败就修到通过。
5. 更新 docs/开发任务.md：勾选条目，进度记录加一行。
6. 本地提交，一个条目一个提交。不推送、不打标签。
7. 用三五行汇报这一项的结果，然后继续下一项。

遇到下面任何一种情况就停下来问我，不要自己绕过去：
- 条目标了“需确认”，或者范围有歧义；
- 关口二连续两次修不过，或者远程连不上；
- 需要新增依赖、改门槛、删除测试，或者要动条目范围之外的文件；
- 需要推送、打标签或发布。

全程用中文回复。测试只在远程执行，本机不跑 go test、vitest 和检查脚本。
```

## 交给 Grok 的提示词

Grok 负责代码、测试和进度记录，测试在远程主机执行；需要拍板的事由它停下来问你。把下面整段原样粘贴给它。

```text
你在星烽 StarBeacon 仓库里做开发。仓库是 https://github.com/kkx600/StarBeacon ，分支 main。请完成 docs/开发任务.md 里的下一个条目，只做这一项。

开工前
1. 通读 AGENTS.md、docs/开发规范.md、docs/测试与发布流程.md、docs/开发任务.md。界面相关的条目再读 DESIGN.md，重点是“改版”一章里的配色、列表、页面说明、配置的位置和用语。条目里点名的设计文档也先读完。
2. 用 git status 和 git log 核对仓库的实际状态，不要只信文档。
3. 在 docs/开发任务.md 里从上往下找到第一个状态不是 [x] 的条目。编号只是名字，不代表先后；[~] 表示做了一部分，先看条目下的“已做”和“剩余”。用几句话复述它的范围、涉及的文件和完成标准。条目标了“需确认”，或者范围有歧义，先停下来问我，不要自己定。

实现
4. 只改这个条目范围内的文件，写法遵守 docs/开发规范.md。几条最容易犯的：
   - Go 代码过 gofmt 和 go vet；业务写入和审计在同一事务；每条查询带租户条件。
   - 前端用 Vue 3 的 <script setup lang="ts">；颜色只用主题变量，源码里不写 #hex 和 rgba()；只面向 PC，最小宽度 1024px。
   - 列表的编号单独成列、一行一条，分页只用共享的 ListPager 或 tablePagination()。
   - 系统级配置只放“系统设置”，业务页面只展示本页内容。
   - 状态用语只用 web/packages/shared/src/terms.ts 里登记的标准词，对照表在 DESIGN.md 的“用语”一节。
   - 注释、文档、界面文字和提交说明用简体中文。
5. 新增或修改的代码必须带测试。Go 和前端的覆盖率门槛都是 90%。不许为了通过而降低门槛、删除测试或跳过检查。
6. 范围外发现的问题不要顺手改，记到 docs/开发任务.md 的“待排期”。
7. docs/开发规范.md 第 8 节里“主会话／子代理”的分工是给 Claude 用的，你不用照做：代码、测试和进度记录都由你完成。规范、流程和设计文档只在条目明确要求时才改。

验证
8. 关口一（本机自检）：按 docs/测试与发布流程.md 里的命令做编译、go vet、gofmt 和两条类型检查，全部通过。
9. 关口二（远程验证）：测试只在远程主机 home_dev 执行。不要在本机运行 go test、vitest、node --test 和各类检查脚本。按 docs/测试与发布流程.md 的方法把源码同步到 home_dev，执行这个条目要求的那几组，失败就修到通过。连不上 home_dev 或条件不具备时，把条目标成 [!] 并写明原因，不要写成通过。
10. 界面改动在你的环境能打开浏览器时要实际看一遍：1440×900 和 1024×768 两种宽度，确认没有报错、页面没有横向溢出。看不了就在汇报里说明没有目视。

收尾
11. 更新 docs/开发任务.md：做完的条目勾选为 [x]，没做完的保持 [~] 并更新“已做”和“剩余”；在“进度记录”加一行，写清日期、结果、跑了哪些验证、没跑哪些、提交号。失败、跳过和没有验证的内容如实写。
12. 提交：一个条目一个提交，说明格式是“<类型>: <中文说明>”，类型取 feat、fix、refactor、style、docs、test、ci、chore。只在本地提交。不推送、不打标签、不发布，除非我明确说。
13. 每轮远程验收结束后，按 AGENTS.md 的“验收结束后的空间清理”清理并记录结果。
14. 汇报后停下：做了什么、验证结果（跑了哪些、没跑哪些）、遗留问题、需要我决定的事。等我说“继续”再做下一项。

当前状态（2026-11-20）
- main 上最近的三个提交包含观察名单命中功能、界面改版与系统设置中心、AI 自动化处置原型和四份新设计文档。它们只过了本机自检，没有在远程验证过。
- 所以第一个条目是 T01：在远程验证这些改动并修复失败项，修复用新的提交。
- 已知 node prototype/scripts/check-screenshots.mjs 会失败，CI 也因此是红的：新增的三个原型页面没有截图。这一项留给紧接着的 T04 处理，不要为了通过去改检查脚本的门槛。

全程用中文回复。
```

想让它一项接一项连续做，把第一段最后一句“只做这一项”改成“按顺序连续完成条目，每个条目都完整走完下面的步骤再开始下一个”，把第 14 步改成“用三五行汇报后继续下一项；遇到‘需确认’、范围有歧义、关口二连续两次修不过、远程连不上、需要新增依赖或改门槛、需要推送或发布时停下来问我”。

## 常用的补充指令

- 指定条目：在提示词第一行后面加一句“这次只做 T05”。
- 只看不改：“读 docs/开发任务.md，告诉我下一个条目是什么、前置条件满足没有，不要改任何文件。”
- 推送：“把本地提交推送到 main，然后告诉我 CI 的结果。”
- 发布：“按 docs/测试与发布流程.md 的关口三发布 v0.2.0-rc.1。”
