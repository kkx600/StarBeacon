# 星烽 StarBeacon 测试与发布流程

所有改动走同一条路。任何一步失败都先修复：不跳过，不放宽门槛，不用另一步的成功顶替。

```text
改动 → 关口一 本机自检 → 关口二 远程验证 → 提交 → 推送（CI 自动检查） → 关口三 发布
```

| 关口 | 什么时候 | 在哪里 | 通过标准 |
| --- | --- | --- | --- |
| 一　本机自检 | 每次改动后 | 本机 | 编译、静态检查、类型检查全部无报错 |
| 二　远程验证 | 每个条目提交前 | 远程主机 `home_dev` | 相关测试无失败、无跳过，覆盖率达标 |
| 三　发布 | 需要出版本时 | GitHub Actions | 标签工作流全部通过，发行包核验一致 |

## 关口一：本机自检

本机只做不执行测试的检查，几分钟内完成。

```sh
CGO_ENABLED=0 go build ./...
CGO_ENABLED=0 go vet ./...
gofmt -l cmd internal migrations tests api/sensor        # 没有输出才算通过
pnpm --dir web typecheck
pnpm --dir prototype exec vue-tsc --noEmit
```

只改文档时不需要运行。代码由子代理修改时，子代理改完先跑一遍，主会话复核时再跑一遍（分工见[开发规范](开发规范.md)第 8 节）。本机工具链版本可能与仓库声明不同，所以直接调用 `go` 和 `pnpm`，不经过 `make` 的版本检查；本机结果只用于尽早发现问题，结论以关口二和 CI 为准。

## 关口二：远程验证

测试只在远程主机 `home_dev` 的专属 Docker 环境执行，不在本机运行。按改动类型决定跑哪几组：

| 改动涉及 | 必须通过 |
| --- | --- |
| 只有文档 | 不需要；改到生成文档或清单时跑“契约” |
| Go 代码、迁移、接口 | 后端全量 + 契约 |
| 前端或原型 | 前端与原型 + 契约 |
| 两者都有 | 全部 |

**后端全量**（单元、真实依赖集成、覆盖率）：

```sh
python3 scripts/remote_acceptance.py stage     # 首次：建立远程项目
python3 scripts/remote_acceptance.py sync      # 同步当前源码
python3 scripts/remote_acceptance.py run       # 构建并执行，结束后看退出状态
python3 scripts/remote_acceptance.py fetch     # 取回报告并回收远程资源
```

**前端与原型**（在远程主机的源码副本里执行）：

```sh
pnpm --dir web install --frozen-lockfile
pnpm --dir prototype install --frozen-lockfile
python3 scripts/qualify_frontend.py --output .local/acceptance/frontend --max-workers 2
node --test prototype/scripts/*.test.mjs
pnpm --dir prototype check:coverage
pnpm --dir prototype check:workspaces
pnpm --dir prototype check:collector
pnpm --dir prototype check:theme
pnpm --dir prototype build
node prototype/scripts/check-screenshots.mjs
```

**契约**（需求清单、接口、路由和页面是否一致）：

```sh
python3 scripts/check_alignment.py --check
python3 -m unittest discover -s tests/quality -v
python3 -m unittest discover -s scripts/tests -v
```

改了 `tests/acceptance/implementation.json` 或接口后，先运行不带 `--check` 的 `python3 scripts/check_alignment.py` 重新生成[功能实现与验收状态](功能实现与验收状态.md)，再跑 `--check`。

通过标准：没有失败和跳过；Go 语句覆盖率不低于 90%；前端语句、分支、函数、行四项均不低于 90%。

前端与原型目前没有一条命令的远程入口，需要先把源码同步到远程再逐条执行。统一入口由[开发任务](开发任务.md) T02 提供，完成后本节改为一条命令。

## 提交与推送

1. 关口一、关口二通过后提交：一个条目一个提交，格式见[开发规范](开发规范.md)第 6 节。
2. 把验证结果在[开发任务](开发任务.md)的进度记录里写一行。
3. 推送须经确认。推送到 `main` 后，`.github/workflows/ci.yml` 自动运行：
   - Go：依赖校验、门禁与工具脚本测试、契约对齐、构建、单元测试、`go vet`、集成测试编译、格式检查、Linux 两种架构交叉编译。
   - 前端与原型：类型检查、组件测试与覆盖率、双端构建、原型检查脚本、截图完整性。
4. CI 失败就立即修，修复作为下一个提交；不在失败的 `main` 上继续叠加新条目。

## 关口三：发布

### 版本号

- 预发布：`v主.次.修订-rc.序号`，例如 `v0.2.0-rc.1`。发布为 GitHub Prerelease。
- 正式版：`v主.次.修订`。
- 已发布的版本不覆盖、标签不移动；要修正就发新版本号。

### 步骤

1. `main` 工作区干净，最新提交的 CI 全部通过。
2. 在同一个提交上完成关口二的全部三组。
3. 按下面的模板写 `docs/releases/<版本>.md` 并提交。它同时是 GitHub Release 的正文。
4. 打附注标签并推送：

   ```sh
   git switch main
   git pull --ff-only
   git tag -a v0.2.0-rc.1 -m "StarBeacon v0.2.0-rc.1"
   git push origin v0.2.0-rc.1
   ```

5. `.github/workflows/release.yml` 自动完成：核对标签 → 复用全部工程检查 → 构建平台与采集器两个 Linux ZIP → 核验发行包 → 发布 GitHub Release。
6. 在 Release 页面确认两个 ZIP 和 `checksums.json` 都在。某一步失败时在 Actions 页面用 Re-run failed jobs 重试，不要移动标签。
7. 做验收清理（见“记录与清理”）。

### 发布记录模板

```markdown
# StarBeacon v0.2.0-rc.1

一句话说明这个版本是什么、适合谁用。

## 本版内容

- 按用户能感知的变化列出，每条一行。

## 检查结果

- 提交：<提交号>
- 后端：单元 N 项、集成 N 项全部通过，Go 覆盖率 N%
- 前端：N 项全部通过，四项覆盖率 N%／N%／N%／N%
- CI 与发行包核验：通过

## 已知问题与边界

- 还没做或没验证的内容，如实列出。
```

### 正式版的额外条件

预发布只要求上面的步骤。正式版还必须同时满足：

1. 核心业务闭环的功能已完成，并通过真实执行验证，不以原型或占位接口代替。逐项缺口见[功能实现与验收状态](功能实现与验收状态.md)。
2. 验收结果与发布提交是同一个提交。
3. 生产部署检查通过：TLS、数据库最小权限、网络隔离、对象存储、原生执行隔离。
4. 两个 Linux 发行包实际启动并完成端到端核验，许可与 SBOM 齐全。
5. PC 全部路由完成布局与必要操作的核对。
6. 部署、回退、升级、留存和恢复的边界可以复核。

目前只具备预发布资格。

## 截图图库

原型截图是设计参考，不是验收门槛。CI 只核对图库文件完整，界面改动后截图过期不阻断合并和发布；但页面目录新增页面后，图库会因为缺少新页面的图片而不完整，需要补拍才能通过。图库将精简为代表图并提供一键重拍脚本，只在发版前重拍一次，见[开发任务](开发任务.md) T04 与 T22。

## 记录与清理

- 每个条目：在[开发任务](开发任务.md)的进度记录写一行（日期、条目、结果、验证结论、提交号）。
- 每次发版：一份 `docs/releases/<版本>.md`。
- 不再维护长篇验收记录。2026-11-20 之前的记录保存在 [archive](archive/)，只供查阅。
- 每轮远程验证或发布结束后清理，规则见[验收环境清理](验收环境清理.md)：

  ```sh
  make acceptance-cleanup-plan      # 先看清单
  make acceptance-cleanup           # 按清单清理本机工程文件
  make acceptance-cleanup-docker    # 清理归属本项目的远程 Docker 资源
  ```

## 遇到失败

- 如实记录失败原因和现象，修复后重新跑完整的一组，不只重跑失败的那一项。
- 不为了通过而改期限、降门槛、删用例或标记跳过。确实需要调整门槛时先提出来确认。
- 外部条件不具备（真实设备、外部账号、生产环境）时记为“未验证”，不记为通过。
