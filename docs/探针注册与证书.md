# 星烽 StarBeacon 探针注册与证书

本文描述当前工程的探针客户端证书链路。生产 CA 高可用、灾备、服务端证书自动轮换及跨故障域资格仍须独立验收；工程用例、协议夹具和原型不代替这些验收。

## 身份与信任边界

探针使用固定的租户、探针标识和注册身份，证书仅包含该身份的规范 SPIFFE URI，并只允许 `clientAuth`。平台不接受设备在消息中自报租户。新探针及恢复凭据只能由本租户当前有效管理员创建，探针私钥由采集器本机生成，平台和 CA 注册接口只接收 CSR。

独立 step-ca 保存中间签发密钥及签发数据库。根私钥位于初始化目录的 `offline/`，不挂载到运行中的 CA；平台仅取得受限 provisioner 的 Ed25519 授权 JWK，不持有根或中间 CA 私钥。该 JWK 能授权本 provisioner 的客户端签发，仍是高敏凭据，必须通过私有文件挂载，不写入环境变量原文、镜像层、仓库、页面、URL 或日志。

平台和事件接入服务的 `SB_TLS_CA` 信任集合须包含探针 CA 根，服务证书须包含实际 gRPC 服务名。采集器使用两份用途明确的根：`SB_TLS_CA` 验证平台及事件接入服务，`SB_IDENTITY_ROOT` 验证独立 CA 签发给本机的客户端证书。服务端证书与探针客户端证书不能混用。

平台、采集器和 CA 使用部署环境的受控时钟同步机制；TLS 与单次签发授权均核验有效时间。多主机时钟偏差及校时故障仍需在实际部署环境验收。

## 依赖与 CA 部署

| 依赖 | 固定版本 | 使用范围 |
| --- | --- | --- |
| step-ca | 0.30.2 | 独立 HTTPS CA；官方镜像 `cr.smallstep.com/smallstep/step-ca:0.30.2@sha256:a2b17872915c193259b75a5474c398326f41bd199f0842093e52cf4182bc8270` |
| go-jose/v4 | v4.1.6 | 标准 JWK、EdDSA JWT 签名；Go 模块摘要由 `go.sum` 核对 |
| step CLI | 随上述固定镜像交付 | 仅用于专属初始化及健康检查；平台运行时直接调用固定 CA HTTPS API |

版本及协议依据：[step-ca 固定发行](https://github.com/smallstep/certificates/releases/tag/v0.30.2)、[CA 配置](https://smallstep.com/docs/step-ca/configuration/)、[被动吊销语义](https://smallstep.com/docs/step-ca/revocation/)、[go-jose 固定发行](https://github.com/go-jose/go-jose/releases/tag/v4.1.6)。step-ca 的被动吊销阻止后续 CA 续签，并不能强制所有依赖方拒绝已签发、尚未过期的证书；StarBeacon 另按持久指纹吊销记录拒绝请求。

初始化工具只接受全新的绝对目录，父目录须已存在，不覆盖已有 CA。以下路径为部署示例，属主须替换为实际运行账号：

CA 初始化工具、Compose 配置和签发模板位于平台发行包对应提交的仓库中，不包含在当前 ZIP 的运行配置中。初始化主机需要 Python 3.9 及以上和 Docker；在线平台与采集器不依赖 Python 处理证书。

```bash
python3 scripts/init_step_ca.py \
  --directory /srv/starbeacon/probe-pki \
  --dns step-ca,localhost,127.0.0.1 \
  --uid 1000 --gid 1000 \
  --platform-uid 65532 --platform-gid 65532
```

`ca/` 为 CA 运行目录，`platform/` 提供根证书和平台授权 JWK，`offline/` 仅保存离线根私钥。初始化容器没有网络、移除全部 capabilities，并使用非 root 账号。失败时保留专属目录用于诊断，不能直接覆盖重试。把离线根及其恢复材料转移到经过验收的离线保管设施后，再按组织流程管理备份和轮换；本工具不提供自动离线托管服务。

在现有 Compose 项目中组合 `deploy/compose.yaml` 和 `deploy/compose.pki.yaml`，启用 `pki` profile，设置 `SB_STEP_CA_DIRECTORY=/srv/starbeacon/probe-pki/ca`。CA 默认仅在 Compose 管理网络内提供 9000 端口，不公开宿主端口；平台容器需加入同一受控网络。使用主机平台服务时，可在独立 override 中把 CA 端口映射为 `127.0.0.1:29000:9000`，平台地址为 `https://localhost:29000`；远程管理地址须显式纳入 CA 的 SAN 和管理网访问控制，不能跳过 TLS 校验。

CA 配置、根与中间证书、密码和模板只读挂载，仅 CA 数据库目录可写。容器限制为 512 MiB、1 CPU、128 PID，使用非 root、只读根文件系统和 `no-new-privileges`。官方 ELF 带有低端口文件能力标记，能力边界仅保留 `NET_BIND_SERVICE` 以满足内核执行检查；CA 仍监听 9000，未使用特权容器或宿主网络。依据见[固定发行 Dockerfile](https://github.com/smallstep/certificates/blob/v0.30.2/docker/Dockerfile)。这些是工程资源起点，不代表大规模签发容量资格。平台不要挂载整个初始化目录，尤其不要挂载 `offline/` 或 CA 的 `secrets/`。容器按文件分别挂载；主机平台服务须把授权文件和根安装到服务账号可遍历的独立私有目录，不应放宽 CA 或离线目录的权限。

### 镜像离线分发

验收服务器不能访问官方镜像仓库时，可在本仓库 `main` 指定提交手动运行“探针 CA 镜像分发”。该工作流只拉取上述固定摘要的 `linux/amd64` 镜像，通过 Docker `image save` 保留全部层、元数据和文件能力，并生成 `image.tar.gz`、`image.json`。制品名为 `starbeacon-probe-ca-image-linux-amd64`，保留三天，不包含 CA 配置、密码或私钥。分发记录只证明镜像来源和归档身份，部署资格以目标服务器的实际执行为准。

通过 GitHub API 保存该运行及其制品目录的原始响应，组成包含 `run`、`artifacts` 两个字段的 `origin.json`，并下载唯一同名制品到全新目录。使用分发运行的实际提交和运行 ID 进行核对：

```bash
python3 scripts/probe_ca_image.py verify \
  --directory .local/acceptance/probe-ca-image \
  --origin .local/acceptance/probe-ca-image-origin.json \
  --repository kkx600/StarBeacon \
  --commit <分发运行的完整提交摘要> --run-id <分发运行ID>
```

校验拒绝不同仓库、分支、提交、工作流、失败运行、过期或重复制品、错误架构、镜像摘要不符、符号链接及归档内容变化。向目标服务器传输后再次校验文件 SHA-256，再用 Docker `image load --input image.tar.gz` 导入，核对实际镜像 ID 与记录一致。导入可能不保留仓库摘要别名，必须使用已经核实的镜像 ID，不按同名 tag 推断镜像身份。初始化工具的 `--image` 及专属 Compose override 的 `step-ca.image` 可引用该 ID，设置 `pull_policy: never`，其余用户、挂载、网络与资源限制保持上述约束。正式部署仍需完成健康检查、签发、续签、吊销和故障恢复验收。

## 平台与探针配置

平台角色独立配置以下值，不应把授权密钥配置复用给 ingest、worker 或 agent：

| 配置 | 含义 |
| --- | --- |
| `SB_PROBE_CA_URL` | 不含路径、查询和片段的 HTTPS 来源，例如 `https://step-ca:9000` |
| `SB_PROBE_CA_ROOT` | CA 根证书的绝对文件路径 |
| `SB_PROBE_CA_PROVISIONER` | 初始化固定为 `starbeacon-probes` |
| `SB_PROBE_CA_JWK` | 平台授权 JWK 的绝对路径，私有普通文件，0600 |
| `SB_PROBE_CERTIFICATE_SECONDS` | 客户端证书有效期，默认 86400 秒，允许 300–604800 秒；CA 也限制为 5 分钟至 168 小时 |

已有静态开发身份不进入托管指纹目录，也不能直接改用生产注册凭据覆盖。静态身份到托管身份的迁移与 WAL 交接仍需独立验收，不以开发兼容模式作为迁移完成证明。未配置 CA 时，已有开发联调证书继续采用原静态方式；页面明确显示“独立 CA 尚未配置”，不能用开发签发工具冒充生产注册。目录中的 `ca_configured` 仅表示适配器已配置，不是 CA 在线检查。

探针采用 `SB_IDENTITY_DIR` 和 `SB_IDENTITY_ROOT` 启用托管身份，不能同时配置静态 `SB_TLS_CERT`、`SB_TLS_KEY`。目录必须为探针运行账号专有的 0700 目录；身份、私钥、待办和旧身份均为 0600 普通文件。独占文件锁防止两个进程管理同一身份目录。生产采集器的本地 HTTPS 管理服务必须通过 `SB_HTTP_TLS_CERT`、`SB_HTTP_TLS_KEY` 使用单独服务端证书。

身份目录位于本机持久文件系统，容器以专属持久目录挂载，不能依赖容器临时层。文件锁、同目录原子替换和文件／目录同步共同构成恢复边界；共享网络文件系统及复制同一身份运行多个采集器的行为未验收。

## 注册与恢复

1. 在“探针管理 → 注册与证书 → 注册凭据”创建凭据，绑定名称、探针标识、注册身份和首次注册有效期。默认一小时，可设 60–86400 秒。恢复已有托管探针时，名称和注册身份必须与目录一致；不能覆盖开发探针或更改已有注册代次。
2. 浏览器以 CSPRNG 生成 32 字节秘密，平台仅保存摘要。相同凭据标识和完全相同输入可重试，不同输入返回冲突。令牌原文只在成功窗口的内存中提供，关闭、退出或切换身份后清除。保存文件后在 Linux 采集器设置 0600 权限。
3. 在采集器本机运行注册命令。以下是占位路径，不含任何真实令牌：

`starbeaconctl` 随平台 ZIP 交付。采集器主机须取得同一版本、同一 Linux 架构的该程序并放入受控可执行路径；注册不需要数据库连接，也不应把平台的运行环境文件或 CA 授权 JWK 复制到采集器。

```bash
starbeaconctl enroll-agent \
  --dir /var/lib/starbeacon/identity \
  --token-file /run/starbeacon/enrollment.token \
  --ca-file /etc/starbeacon/trust/probe-root.crt \
  --platform-ca-file /etc/starbeacon/trust/platform-root.crt \
  --platform-url https://console.example
```

注册工具必须以探针运行账号执行，使 0700 目录和 0600 私钥文件始终由同一服务账号持有；不要以公开读权限解决属主错误。工具先持久保存 CSR、私钥和凭据摘要，再发送请求。平台先持久绑定签发记录，再请求 CA，独立核验返回链、原公钥、身份、用途和有效期，并提交指纹后才返回成功。注册期间停用探针、撤销令牌或停用创建人权限，均不能登记为可用证书。设备交换不继承浏览器会话，拒绝带 `Origin` 或 `Sec-Fetch-Site` 的请求。

同一有效令牌和 CSR 在完成签发后可重取相同证书；不能替换 CSR。CA 回执中断、签发进程退出或持久登记结果无法核实时，保留“结果待核实”，不自动重签。新签发记录超过一分钟仍在签发中时，由历史维护调度转入待核实状态；这不是签发失败或 CA 未签发的证明。

身份过期、私钥丢失或未知提交无法恢复时，管理员先核对原记录并撤销原凭据及已知证书，再为相同探针名称和注册身份创建独立凭据。停止该探针进程，用**全新私有身份目录**执行注册，再修改 `SB_IDENTITY_DIR` 并重启；原待办和身份目录保留供核对。不能删除 WAL 或更换租户、探针、注册身份来消除绑定错误。该显式恢复不自动迁移租户、不自动注销仍有效的其他证书，也不伪造未知 CA 序列号的吊销确认。

## 自动续签与吊销

采集器每 30 秒检查一次，在当前证书最后三分之一有效期进入续签。每张父证书只绑定一个持久 CSR，重试保持同一请求。新证书须分别通过平台与事件接入端的实际 mTLS 指纹认证，之后原子发布单个证书／私钥文件、保留一份旧身份，并切换数据、控制及原包连接。切换失败不清空 WAL、不重置任务回执，也不以文件存在推定链路已经恢复。

续签失败保留旧身份及原待办，在运行状态记录 `certificate_renewal_unavailable`。旧证书仍有效时可以继续上报；证书过期后拒绝通信，需要上述显式恢复。新旧证书在各自有效期内可以重叠，平台不把新证书签发成功自动解释为旧证书已吊销。

吊销分两步：平台事务先登记拒绝该实际指纹，随后请求 CA 被动吊销。`pending`／`unknown` 与 `confirmed` 独立展示，CA 请求失败不能撤销平台拒绝记录。逐次 RPC、数据帧、样本和原包请求检查证书有效期、当前注册身份、探针启用状态及指纹；已有控制流每五秒复核，即使未启用任务分发也执行。该周期不是严格的端到端 SLA，还受数据库可用性和调度影响。仅撤销注册令牌不影响已经签发的证书；停止整台探针应停用探针并核对全部有效证书及未结响应职责。

CA 的单次授权和回执存在网络未知窗口。重试不能把“已使用授权”或“已经吊销”的模糊错误文本当作可核实确认；没有明确成功回执时继续保留待核实状态，需由 CA 管理员独立对账。目前不提供通用 CRL／OCSP 发布或自动 CA 对账接口。

## 数据留存、页面与验收

注册记录在凭据到期后按操作留存策略保留，证书记录至少覆盖证书有效期及之后的操作留存期，默认均为 180 天，后续创建记录采用用户配置。活动证书、未完成签发和当前身份不按短期缓存回收。证书认证有效期默认 24 小时，与业务记录的 180 天留存完全独立。证书目录不返回 CSR、证书链或任何私钥；本地页面只展示本机当前发布的摘要、时间和续签窗口，不代表平台当前允许通信。

平台在原探针工作区使用“注册与证书”页签，凭据和证书为互斥列表，创建、详情和撤销使用弹窗。未确认提交锁定原参数、提供原请求核对入口，不能误报为空列表或成功。采集器“网络与采集 → 网卡与状态”提供只读通信身份；权限变化、页面卸载和过时响应都会清理或取消本次状态。原型复用相同表单和详情组件，全部示例明确标识合成数据。

测试入口包括 `internal/probepki` 的密码材料与文件失败用例、平台 HTTP 拒绝边界、真实 PG 事务／权限隔离、独立 step-ca 容器签发与实际时钟自动续签、旧存量控制连接拒绝、新证书独立有效和探针停用。实际执行结果统一见[测试覆盖与验收记录](测试覆盖与验收记录.md)，未取得结果的项目不宣称通过。签发中间件夹具仅验证故障边界；从官方发行文件构建的工程 CA 镜像不等同于官方生产容器资格。

实际程序验证可在已通过后端与真实网卡门禁、且启用独立 CA 的专属验收项目中运行 `python3 scripts/accept_probe_pki_programs.py --state .local/acceptance/remote.json --output .local/acceptance/probe-programs`。驱动拒绝不同源码、未通过门禁、目录复用和输出越界，保留实际容器身份、退出码、各 Go 程序摘要、原始日志及结果。该用例使用测试 TLS 注册网关及共享角色文件系统，验证的是实际程序启动、mTLS 事件上报、实际时钟续签与 CA 吊销后的新证书上报；EVE 是明确标识的合成事件，不授予原生捕获、生产 TLS、凭据故障域或 HA 资格。

当前冻结来源的工程回归、实际程序验证、远程部署及清理范围见[探针注册与证书验收证据](验收证据/2026-10-17-探针注册与证书.json)。常驻工程实例保留原静态身份；独立 CA 流程的验证不构成静态身份迁移、官方生产容器或高可用资格。
